# Anta-Vista — Agent Guide

## Workspace
- Rust workspace, `resolver = "2"`, **no toolchain file** — build with `stable` (no `rust-toolchain` file pins a version). All crates `edition = "2024"`, version `0.2.0`.
- No `.cargo/config`, no `rustfmt.toml`, no `clippy.toml`.
- **Binary**: `av-cli` publishes the `av` binary (`crates/av-cli/src/main.rs`). All other crates are libraries.
- **Crate dependency graph** (bottom-up, a fan not a chain):
  `av-core` → `av-store`, `av-embed`, `av-ingest`, `av-net-x0x` → `av-trust`, `av-index` → `av-query` → `av-cli`, `av-probe`, `av-test-suite`.
  Note: `av-query` depends only on `av-core`/`av-store`/`av-trust`/`av-net-x0x` — it **bypasses** `av-index`/`av-embed`. Do not add `av-query → av-index` deps without reason.
- `ANTA_VISTA_DB_PATH` env var overrides the default SQLite db path (derived from `directories::ProjectDirs` via `av_core::paths::db_path`).

## URI scheme (easy to get wrong)
- Canonical scheme is **`autonomi://`** (flipped from `ant://` in commit `408e97c`, with DB migration `004_canonical_scheme`).
- `ant://` is accepted as an **input alias** only — `av_core::constants::{ANT_SCHEME, AUTONOMI_SCHEME}` and `normalize_scheme()` map `ant` → `autonomi`; indexing/ranking normalize stored targets to `autonomi://`.
- Bare 64-hex strings (no scheme) are auto-prefixed with `autonomi://` (in `av-ingest/src/location.rs` `normalize_uri`).
- New URI-handling code should treat `autonomi` as canonical and normalize aliases early via `av_core` helpers.

## Git
- **Never run `git commit` unless the user asks for that commit in that message.** Finishing a task is not permission to commit. Approval to commit once is not standing approval — a later "remove X and Y" still means edit the working tree and stop, leaving `git status` dirty for review.
- Commit only when the request explicitly names committing ("commit this", "make a commit"), and never bundle unrelated work into a commit just because the tree is already staged.
- `git add`/`git rm` to inspect or stage is fine, but if staging was only for review, say so and leave it staged rather than committing.
- Never `push` without being asked. Both commits in the web-GUI line of work are local only.

## Testing quirks
- **x0x live-daemon tests** (`av-test-suite/tests/x0x_live_daemon.rs`) are `#[ignore]` **and** body-guarded by `skip_if_no_daemon()`. The guard is *discovery-based*, not a health probe: it checks the x0x data dir (`ProjectDirs::from("", "", "x0x")`) for readable `api.port` + `api-token` files. Runs only with `--include-ignored`.
- `skip_if_no_daemon()` / `inject_gossip_payload()` / `spawn_named_instance()` live in `av-test-suite/src/x0x_harness.rs`.
- `av-test-suite` has no `[[test]]` entries in `Cargo.toml` but **does** ship integration tests via auto-discovery (`tests/av_*.rs`, `integration_*.rs`) alongside its shared helpers (`fixtures`, `generators`, `attacks`, `prelude`). Both run under `cargo test -p av-test-suite`.
- Real MiniLM model tests (`--include-ignored`) download ~87 MB on first run via `fastembed`/ORT, cached under the OS cache dir (`av_core::paths::cache_dir`); `FASTEMBED_CACHE_DIR` overrides it.
- `proptest` is a workspace dependency — property-based tests exist but are not run as a separate gate.

## CLI
```sh
av <subcommand> [options]
```
Subcommands: `web`, `status`, `resolve <name>`, `search <query>`, `name <uri> <name>`, `index <uri>`, `rate <resource_id> <rating>`, `block`, `unblock`, `purge`, `listen`, `stop`, `propagate <resource_id> <location> <description>`.
Flags: `--non-interactive` (JSON machine mode; may appear before or after subcommand), `--config <path>`, `--timeout <ms>` (default 10000), `--stream`, `-v`/`-vv`.

- **Bare `av`** is now valid: `cli.command` is an `Option<Commands>`, and `None` launches the web interface. `is_offline_command(None)` is true, so bare `av` starts with no x0x installed. Machine mode must still refuse: bare `av --non-interactive` returns `{"ok":false,"error":"no_subcommand"}` with **exit 2** (asserted in `cli_tests.rs`).
- **Startup gating** (`crates/av-cli/src/startup.rs`): `status`, `purge`, `listen`, `stop`, `block` and `unblock` run offline; `resolve`/`search`/`name`/`index`/`rate` require an x0x daemon. In interactive mode the CLI offers to install/start x0x, and `name`/`index` offer the ant CLI + `antd` daemon (port 8082) for `ant://` URIs — keep this flow in mind when touching CLI. `block`/`unblock` are offline because blocking a misbehaving peer has to work when the daemon is unavailable.
- **Machine-mode** (`--non-interactive`) exits with JSON errors instead of prompting; missing deps are hard errors there.
- **Listener management** (`crates/av-cli/src/listener.rs`): `av listen` writes `<data_dir>/av-listener.pid` (protected by a `PidFileGuard` drop-guard in `cmd/listen.rs` so a crash/timeout rarely leaves a stale PID). `stop_all()` computes every running listener — `/proc` cmdline sweep for `av ... listen` (unix) ∪ PID-file PID — SIGTERM then SIGKILL after ~3s (`--force` skips the grace period), and clears the PID file. `ensure_running()` is called from startup for network commands and spawns a detached `av listen` from `current_exe` if `is_running()` is false; it only checks aliveness, so an old binary never triggers a respawn by itself — use `av stop` then the next network command to upgrade the responder.

## Web interface
`crates/av-cli/src/web/` + `crates/av-cli/assets/`, served in-process by `tiny_http`. Launched by `av web`, `av gui`, or bare interactive `av`.

- **Reuse the CLI, don't reimplement it.** `web/handlers.rs` calls `cmd::search::collect_results`, `cmd::search::reinforce`, `cmd::rate::record_feedback`, `cmd::rate::is_locally_indexed`, `cmd::index::index_resource` and `cmd::status::database_counts`. If a behaviour changes in `cmd/`, the browser must change with it — extend the shared function rather than adding a web-only copy. `web` deliberately does **not** depend on `av-index`/`av-embed` crates directly.
- **Startup state is a live snapshot, not a boot constant.** `AppState.startup` is an `RwLock<StartupState>`. Search decides whether to fan out to peers from `startup.x0x_config`, so starting a daemon from the setup banner is useless unless `refresh_network_deps()` runs. Every start/install handler calls it. Handlers take one read guard for the whole request rather than re-reading, so a mid-request change cannot alter the fan-out.
- **`miniLM` loads lazily** (`EmbeddingCache(OnceLock<Result<Arc<MiniLmProvider>, String>>)`) — binding the socket must not wait on an ~87 MB model. Success *and* failure are cached so a broken cache isn't retried per keystroke.
- **Per-request `av_store::open()`** is required (`Connection` isn't `Sync`). This is why `av-store`'s migration bookkeeping uses `INSERT OR IGNORE`: several threads can reach a fresh database at once, all see the migrations as pending, and all of the DDL is idempotent. `web/mod.rs` also pre-warms the database before binding so the race is not hit in practice. Covered by `test_concurrent_opens_of_a_fresh_database` in `av-store/tests/on_disk.rs`.
- **Shutdown is a poll, not `Server::unblock()`.** `tiny_http::Server::unblock()` releases exactly **one** waiting thread ("If there are several such threads, only one is unblocked"), so a 4-worker pool would hang on `--run-for`. Workers use `recv_timeout(200ms)` against an `AtomicBool` instead.
- **Host-header guard** rejects anything that isn't a loopback name, which is the DNS-rebinding defence for a loopback-bound server. Keep it in front of every route.
- **`hidden` is how this UI shows and hides things, and an author `display` rule defeats it.** The browser's `[hidden] { display: none }` lives in the *user-agent* stylesheet, so any author rule that sets `display` silently outranks it — no specificity contest to notice, because the losing rule is in a different origin's stylesheet. `.drawer` and `.banner` are both `display: flex`, which made the status drawer and the setup banner painted from first paint, and made the drawer's close button set `hidden = true` and visibly do nothing: a dead-looking × that was working correctly. The `[hidden] { display: none !important; }` guard at the top of `modern.css` is load-bearing, not decoration — it has to be `!important` to beat a same-origin author rule. It covers retro.css too (which sets no `display` on either panel) because it is unguarded by theme. If you add a `display` rule to anything `app.js` toggles, the guard is what saves you; do not remove it. `hidden_wins_over_the_layout_rules_of_the_panels_it_hides` pins both halves — the guard, and that `.drawer`/`.banner` are still `display: flex` so the guard stays necessary.
- **The status trigger is a toggle, and the drawer must leave room to be dismissed.** `setStatusOpen` owns the state; the trigger derives the next state from `ui.statusDrawer.hidden` and its label and `aria-expanded` both follow, so it reads correctly while collapsed. The drawer is capped at `min(26rem, calc(100vw - 3rem))`: at `26rem` it is wider than a phone viewport, and full-bleed meant it covered the header, so the trigger was underneath it too and the overlay click-out was unreachable — the only way out was the ×. `.drawer-head`/`.drawer-foot` are `flex: 0 0 auto` because `.drawer-body` is `flex: 1` (basis 0, so it contributes nothing to shrink) and would otherwise leave the header absorbing all the shrink, clipping the close button on a short viewport with a long status list.
- **Assert on CSS with `css_rule`, not `contains`.** `modern.css` carries comments that name the very selectors a test looks for, so a `contains` or a fixed character window around a match starts passing for the wrong reason. `css_rule` strips comments and matches whole selectors. `css_rule_lookup_finds_a_rule_and_ignores_prose` guards the helper itself.
- **Test harness quirks** (`crates/av-cli/tests/web_tests.rs`): reads the child's stdout **byte at a time** and only parses port numbers out of *complete* lines — reading a byte at a time and testing after each one parses the half-arrived `"8787"` as `87`. stderr is drained on a background thread (an undrained pipe fills and blocks the child, and hides why a server died). `connect` retries. Tests must not assume the host lacks `x0x`/`ant`; the Autonomi tests assert the invariant that holds either way.
- **The web `/api/block` cannot escalate to x0x at all.** It rejects a caller-supplied `x0x` field with a 400 rather than ignoring it, because a loopback server is reachable by any page the user has open. `av block --agent <id> --x0x` is the only route. Warning text comes from `cmd::block::warning_for` so browser and terminal cannot drift.
- **UI honesty rules.** Repeatable-but-true warnings ("peers do not consume feedback yet") are shown and offer "don't show again" (`anta-vista-muted-warnings` in `localStorage`, keyed by the server's `warning_id` — a *different* warning still gets through). Install commands come from the **server** (`ant_install_command()`) and travel with the error, so the page never hardcodes a POSIX command and shows the wrong one on Windows. `/api/download` is a **real daemon fetch**, not a stub: it returns bytes with the shared MIME policy, `502 download_failed` when the fetch fails, and `503 no_download_backend` (carrying the install command) when neither antd nor the ant CLI exists. See *Autonomi in the browser* below.
- **A result row leads with its identifier; the description goes underneath, in both the CLI and the browser.** `av search` prints `location` then an indented `description`, and the browser now matches it for every source. Do not branch row layout on the location's *scheme*: that is what made `http(s)` results use `description` as their link text (hiding the URL entirely) while Autonomi results showed the location, so the same field rendered two ways. `source: "name"` inverts deliberately — the name is the heading and the location is the target it resolves to, which is why `cmd/search.rs` prints it `name → target`. `result.description` is the text anta-vista **embeds**, so for a text or PDF document it is up to 800 characters of the file's own content (`synthesize` in `av-ingest/src/describe.rs`); it must never be a heading or a dialog sentence. The remove confirm names the resource by `result.location` for the same reason.
- **Result actions are Recommend / Remove / Block, and the last two are not the same verb.** "Recommend" posts `rating: "useful"` (the value is unchanged; only the label is) and is the *only* action that can share a link, so it confirms first for `source: "network"` and does not for `source: "local"`. No/Escape must be a complete no-op — no request, no disabled buttons, no status. "Remove from local index" is `POST /api/purge` → `cmd::purge::purge_resource`, which frees local rows and writes **no block**, so a peer can return the link; it is offered only for `source: "local"`. "Block" is the durable one. Never word Remove as though it stopped the link arriving, and never word Block as though it restored anything.
- **Removing or blocking a result must not re-run the search.** Both use `dropResult`/`dropResultsFromAgent` in `app.js` and report through `#results-note`, which lives outside the rows because the row takes its own status line with it. The three `ui.form.requestSubmit()` calls that used to be there re-queried the network — which is a second chance for a peer to hand straight back the link the user just removed. A test asserts `requestSubmit` stays out of `app.js`.
- **An agent block is not a disconnect, and the peer dialog has to say so.** An agent block drops the peer's search responses *and* the names it published, but it does not disconnect it — `av block --agent <id> --x0x` is the transport route, and the dialog only offers that command to run, because the loopback `/api/block` cannot escalate. The dialog also says indexed links stay and the block is reversible with `av unblock`. It uses `#peer-block-blurb { white-space: pre-line }` for the command block. **Do not reintroduce the old claim that "names this peer has already published still resolve, because those are stored locally"** — it was true while an agent block only filtered search responses, and became false once name records carried a transport origin. `web_tests.rs` asserts the phrasing is absent. Do not add x0x escalation here, and do not pad the dialog back out with limits the code now enforces itself.
- **Known gaps to keep in mind:** search blocks (SSE is the follow-up); peers do not consume `av.feedback.v1`, `av.claim.v1` or `av.presence.v1` messages, so a broadcast rating changes nobody's ranking. Nothing ever *emits* an `av.claim.v1` either: the `claims` table, `ClaimPayload`, `MessageKind::Claim` and `TOPIC_CLAIM` all exist and the responder subscribes, but there is no `publish_claim` and no receive arm, so `claims` is always empty and the 0.15 `agreement` weight in `av-trust::ranking` is a constant 0.5 that cannot reorder results. Do not treat agreement as a live ranking signal, and do not add a claim producer without solving the Sybil problem first — `docs/follow-ups.md` has the write-up and a user-mediated replacement; `NameRecord`s cannot receive feedback because `feedback_events.resource_id` references `resources(id)`; `--kind watchlist` becomes `ResourceKind::Other("watchlist")` (unrelated to the web UI, but do not add a kind dropdown until fixed).

- **Search/resolve fan-out** (`crates/av-cli/src/network.rs`): queries go out BOTH as direct messages AND as a gossip broadcast. Direct fan-out candidates = recent `peer_cache` entries ∪ x0x-discovered agents (`/agents/discovered`, `/presence/online` via `X0xNetClient::discover_agent_ids`), deduped, self excluded — so peers never contacted before (and online-only peers) are still queried. Direct queries are sent from detached threads per candidate, each with its own `query_id` registered **before** the send, and `send_direct` permits slow relay/`gossip_inbox` routing (90 s HTTP timeout) — a past bug gated sends on a 2 s `connect_agent`, silently dropping every relay-routed peer. Responses match by any issued `query_id` (direct ids differ from the gossip id). Direct messaging is the fast path; gossip is mesh-driven and slower.

## Autonomi in the browser
`crates/av-cli/src/web/viewer.rs`, the vendored SDK, and the `av web` assets. The browser fetches Autonomi records itself over WebRTC, so an Autonomi link can be viewed and indexed with **nothing installed** — no `ant` CLI, no `antd`. The daemon path remains, explicitly, as a fallback.

- **The SDK is vendored, pinned and MIT/Apache-2.0.** `assets/vendor/ant-browser-sdk/0.1.1/` holds the **complete reachable import graph — all 26 files**, ~5.6 MB, dominated by the 5.4 MB `wasm/ant_core_bg.wasm`. It is vendored whole on purpose: a hand-trimmed subset looks like dead weight until a dynamic import inside a worker resolves a file that was dropped. `.map`/`.d.ts` are excluded. `SDK_VERSION` in `render.rs` is the single pin. Each file needs an `include_bytes!` arm in `render.rs` and is served at `SDK_BASE` (`/assets/vendor/autonomi-sdk/0.1.1/`) — note the runtime prefix is *not* the directory name. `the_vendored_sdk_is_served_with_types_the_browser_accepts` pins the WASM MIME (`application/wasm`; `application/octet-stream` fails to stream-compile) and that the page's boot global matches the served path.
- **An Autonomi location is openable, so it must look and behave openable.** `.result-loc` used to carry `cursor: help` plus a comment claiming an Autonomi location had "no open/download path yet" — which by then was false. It underlined on hover, showed a question-mark cursor, and did nothing when clicked, which reads as broken rather than as a deliberate choice. It is now a `<span>` (never an `autonomi://` href) that app.js wires a click and a key handler on, marks `is-openable`, and gives `role="button"` + `tabindex="0"`. **Set the class, the role, the tabindex and the handlers together in `wireFetch`** — that is the one place that decides the element is openable, and splitting the affordance from the handler is how the two drifted apart. The CSS keeps the inert state and the openable state distinct in *both* themes (`modern.css` and `retro.css`), because a link-shaped element that underlines and lies is worse than one that looks plainly inert.
- **Never upload a file to learn its name.** `POST /api/view/plan` takes the URI, an optional `X-Anta-Mime` hint, and **at most a 16 KB prefix** of the bytes (`blob.slice(0, PLAN_PREFIX)` against the server's `PLAN_PREFIX_CAP`, refused over — never clamped, per the `MAX_BODY` rule), and answers `{filename, renderable, mime_type}`. Both Save and the oversize branch of Open use it. This exists because both used to `POST /api/view/blob` purely to read a filename back, which meant a 64 MB record — fetched successfully — then failed with `request body is larger than the 33554432 byte limit`. That is a confusing error for a successful fetch, and `indexAutonomiInBrowser` already avoided it by checking size *before* uploading. The prefix exists because the SDK reports `application/octet-stream` for most records, so a hint-only plan cannot tell a JPEG from a blob. `opening_severs_the_opener_and_saving_never_uploads_the_file` pins that Save never routes the file through `postBlob` and that `postPlan` slices rather than sending the whole blob; `the_client_and_server_agree_on_the_prefix_cap` pins the two constants against each other, since they live in two languages.
- **`is_browser_renderable` in `av-ingest` is the only copy of "can a browser display this?"** and its bias is towards no. The viewer picks `inline` versus `attachment` from it, and `/api/view/plan` reports the same verdict to the page, so the two cannot disagree. A hardcoded `inline` is what made an undisplayable type show as an empty window with no error and no download. **A hint that cannot be placed is treated as unknown, which answers "download it"** — guessing "renderable" from a generic type is how the blank window happened.
- **`detect_mime_prefix` exists because the SDK reports `raw.file.content_type || "application/octet-stream"` for most records**, so a hint-only plan downloaded every real image and PDF. It shares one private core with `detect_mime` via a `Confidence::Full | Prefix` parameter, so the two cannot drift on what a type *is*. **The rule: a prefix may confirm a specific type, never assert a generic one.** Magic bytes and the `<!doctype html` marker are positive signals that survive truncation; "this whole file is text" is inferred from the *absence* of binary structure, and a prefix cannot establish an absence — the invalid UTF-8 usually sits past the first few KB. So a prefix that decodes cleanly answers `application/octet-stream`, **not** `text/plain`, even though the same bytes as a whole file legitimately sniff as text. That is deliberate: guessing text marks the record displayable and then shows mojibake, whereas the honest answer downloads it, which always works. `a_prefix_that_decodes_cleanly_is_not_called_text` pins the contrast. Do not "fix" this by trusting the hint more, and do not add a second allowlist.
- **A failed fetch explains itself in the tab it opened.** `GET /view/error?code=<enum>` is a standalone page: no app.js, no stylesheet, no API access, and a fixed code-to-message table. The tab is no longer closed on error — a tab that vanishes leaves the explanation behind it, in a row on a page the user must go back to. **The only input is that enum**, so an SDK error string can never be reflected; it is written into the row's status line with `textContent` instead.
- **Opening a tab severs `window.opener` by hand: `tab.opener = null`.** `window.open`'s `noopener` feature cannot be used here because it makes the call return `null`, and the handle is what the finished file is loaded into. Cross-origin stops a fetched document *reading* the app, but nothing stopped it *navigating* the app, and peer-supplied HTML is exactly the untrusted input. `js_code` in `web_tests.rs` strips comments before asserting this, for the same reason `css_rule` does.

- **`window.open` must happen synchronously, before the first `await`, from whatever starts the open.** Both the Open button and a click on the location call the same `openView`, and it opens the tab as its first statement — a popup opened after an await has no user gesture and browsers block it. `an_autonomi_location_looks_clickable_because_it_is` pins the cursor, the role, the key handler and the absence of `cursor: help`.
- **`app.js` is a classic script, so the SDK must be `import()`ed dynamically**, lazily, from `window.__AV_SDK_BASE__`. Loading it eagerly would make page load wait on 5.4 MB of WASM. `loadSdk()` caches the promise *including its failure*: a browser that cannot run it should say so once, not on every click. `autonomiCapability()` asks the SDK's own `getBrowserCapabilities()` once and states the reason where the button is, rather than offering an Open that fails.
- **The SDK wants a bare 64-hex address.** `autonomiAddress()` strips `autonomi://` and any `/name` or `?name=` segment; a scheme-prefixed value is rejected with a misleading "expected 32 hexadecimal bytes". `autonomiAddress()` returning `null` means "not an Autonomi link" and the row is left as plain text — **never an `autonomi://` href**, since nothing handles that scheme.
- **Never trust the SDK's filename.** `file.name` is always a synthetic `public-file-<8hex>.bin`, so every saved file would land under the same meaningless name. The server supplies the name instead, from `av_ingest::filename::suggest_filename`, sanitized to one path segment because it is attacker-influenced and ends up in a download directory.
- **A download is named from the location, and an extension is added only when the author left one off.** The author's own name wins: a trailing path segment, else `?name=` (which used to be ignored entirely — a path-less `autonomi://<hex>?name=report` fell back to an address-derived name, even though the location layer had parsed it all along). The name comes from `location::last_url_segment`/`analyze_location` rather than a second hand-rolled split, so percent-decoding cannot drift. **An extension that is already there is never replaced** — an unrecognised one is still the author's, and overriding it would let the content rename the file they published. When there is none, the sniffed type supplies one (`photo` + JPEG → `photo.jpg`), because a file saved as `photo` is one the OS cannot open. `trusted_extension` in `av-ingest` is the single definition of "has an extension" for both this and the type-tie-breaking in `detect_mime_with_hint`: a name we would not break a MIME tie on is also a name we will not append to.
- **`extension_for_mime` is the exact inverse of `HINTED_TYPES`, and the pairing is pinned.** A type we are willing to *resolve* on a name must also be a type we can *name* — they answer the same question from opposite directions ("what does `.csv` mean?" and "what do we call a `text/csv`?"). They disagreed for ten types (`image/avif`, `text/csv`, `audio/flac` and others could be resolved but never named, so a file the user's own URL identified was downloaded as an untyped blob), and nothing but `every_type_we_would_resolve_can_also_be_named` would have caught it, because adding to either list alone looks correct.
- **`text/markdown` is recognised by convention, not signature, and is deliberately *not* renderable.** `infer` has no magic number for markdown, so `looks_like_markdown` looks for a convention instead: front matter, or an ATX heading opening the file. This is acceptable where the HTML marker is not, because both candidates are *text* — a false positive is `text/markdown` for a really-plain file, whose only consequence is whether the saved file is called `.md` or `.txt`. It is not renderable because a browser handed `text/markdown` treats it as an unknown type and downloads it, so claiming otherwise is exactly the blank-window case `is_browser_renderable` exists to prevent. Recall is partial and that is fine: a markdown file opening with a paragraph has no marker and keeps the `text/plain` answer rather than being guessed at. The marker only runs after the bytes decode as UTF-8, so it cannot talk a binary into being text.
- **Subscribe to progress on `connect()` *and* `download()`.** `download()` only emits `downloading`/`complete`; the phases a user watches — connecting, looking up which nodes hold the file — are emitted during `connect()`. Subscribing to the download alone leaves the status line blank for the ~6 s a lookup takes *regardless of file size*, which is exactly when a user concludes it is broken. Key failures on `err.code` (`DOWNLOAD_FAILED`), never on message text; a nonfatal `WebRTC: ICE failed` is seed failover, so only a settled failure is reported.
- **`window.open` must happen synchronously, before the first `await`.** A popup opened after an await has no user gesture behind it and browsers block it, so the tab is opened on click and `location.replace`d once the URL arrives. If the tab was blocked, say so and keep the bytes — do not silently drop them.
- **Browser-first indexing falls back to the daemon *explicitly*.** `indexAutonomiInBrowser()` returns `null` for a non-Autonomi location (a decline, not a failure) and throws `DaemonFallback` when the browser cannot or should not fetch — no capability, a failed WebRTC transfer, or a file over `MAX_UPLOAD`. `DaemonFallback` is a *routing decision*, never shown to the user as an error, and the success message names the transport that ran ("via your browser" / "via the local daemon"), because "indexed" otherwise means two different things. The size check is **before** the upload: the bytes are already in hand, so sending them to be rejected wastes the transfer.
- **`MAX_BODY` is refused, never clamped.** `read_body_bytes` reads one byte past the cap and answers `400 body_too_large`; the old JSON `read` truncated via `Read::take`, which for these endpoints would have indexed a *corrupt prefix* of a large file under the resource id of those partial bytes and reported success. The refusal carries `RouteError::Ready`, not `Internal` — collapsing it would report a client-side limit as a 500.
- **The viewer's separate port is a security boundary, not a convenience.** Fetched bytes are served by a throwaway `127.0.0.1:0` listener at `/v/<uuid-v4>`, inline, `nosniff`, `no-store`, `no-referrer`, GET/HEAD only, loopback `Host` only, expiring in 120 s. A second port is a second origin, so a hostile document cannot reach `/api/*` — and the `Sec-Fetch-Site: cross-site` guard on POST is the second half of that same protection, because a different port *is* a different site. **Relaxing either half makes serving `text/html` and `image/svg+xml` unsafe**, so those two MIME hints are licensed by this pair, not by the sniff policy alone. There is no cookie and no shared secret: the unguessable token path is the *entire* authorization, and `the_viewer_only_serves_its_own_token` pins that a neighbouring path is a 404.
- **The MIME policy is shared, and it is extension-over-generic only.** `detect_mime_with_hint` lets a short, alphanumeric extension break ties *only* where sniffing is weak (`text/plain` / `application/octet-stream`); content always wins when it is specific, so a `.html` name cannot turn a real PNG into markup. This lives in `av-ingest` rather than the web layer so a stored `mime_type` and the type a download is served as cannot disagree. `detect_mime_with_hint` is also what a `.html`/`.svg` record needs to have any extractable text to embed at all.
- **Known gaps — do not paper over these in the UI.** `Open` fetches **one record**: a single-file viewer, so *absolute* `http(s)` subresources load but *relative* ones fail, and `autonomi://` subresources are unreachable without a browser-side crawl that does not exist yet. `try.autonomi.com` itself is a multi-file site behind a strict CSP and will *not* work as one blob. Folder/manifest support is expected upstream rather than reimplemented here. Downloads are also bounded by the DataMap's reachable seed set, which is small; a very large file can time out even though a small one succeeds.

## Local blocking
`blocks` table, migration `005_blocks`, repo at `crates/av-store/src/repo/blocks.rs`. Three **independent** kinds: `resource` (`resources.id`), `name` (`name_records.record_id`), `agent` (64-hex x0x id). CLI in `crates/av-cli/src/cmd/block.rs`; web at `/api/block`, `/api/unblock`, `/api/blocks`.

- **The invariant: a blocked resource is never served, and a blocked agent is never consulted.** Any new egress path must re-check. Current guard points: `av_index::search::search_top_k` and `av_index::naming::lookup_name` (primary — also what the responder reads from), `to_publishable_resources`/`to_publishable_names` in `cmd/listen.rs` (pre-send, catches `--keep-local` resources that still have embeddings), the `--x0x` agent filter in `network.rs` (both candidate lists and response drops), `propagate_resource` (shared by `av propagate`, the search prompt and the web rating handler), and an early refusal in `cmd::index::index_resource` before any store write.
- **A name block is not a resource block.** `NameRecord` stores a URI, not a `resources` id, so a resource block has to be bridged by resolving the target through `resources::get_by_location`. `av_index::naming::retain_unblocked_targets` is that bridge, and both name-serving paths call it: `lookup_name` (which the responder reads directly) and `to_publishable_names` in `cmd/listen.rs`. `cmd/name.rs` and `cmd/index.rs` both normalise with `av_ingest::location::normalize_uri`, so `target` and `resources.location` share a form; `target_canonical` is the fallback for records that arrived from a peer carrying the legacy `ant://` scheme. The bridge only recognises targets this machine still holds, so after a *delete* there is nothing left to resolve against and a re-supplied claim can be served — see `docs/known-limitations.md`. Do not treat "unresolvable" as "blocked": dropping every name whose target is not held locally would let one block censor the whole local namespace. Do distinguish *not held* from *lookup failed*: `resolve_target_resource` returns `Ok(None)` for the first and `Err` for the second, and the `Err` must propagate. Collapsing them with `if let Ok(Some(..))` turns a broken `resources` table into "we hold nothing", which is the fail-open bug this file already warns about elsewhere.

  All three block kinds that can affect a name now load through one place, `av_index::naming::NameBlockPolicy::load`, and are applied by `retain_unblocked`. `lookup_name` and `to_publishable_names` both call it, which is the point: they used to open the block table separately and could drift. Add a block kind by extending the policy, never by reading `blocks` in a caller.
- **Do not add a provenance column to `resources` to enable resource→agent blocking.** The kinds are independent by design: anta-vista does not know who sent a resource, and inferring it would let one bad result condemn a useful peer. `ClusteredResult.agent_ids` preserves transport origin for *display* so a human can block a peer deliberately.
- **`name_records.origin_agent_id` is the one provenance column, and it is local-only.** Migration `006_name_origin`; the field is `#[serde(skip)]` on `NameRecord`, and `types.rs` tests pin that a peer cannot set or see it. A name block by resource id is bridged through the target, but an *agent* block has nothing to match without it, because `NameRecord.by_agent_id` is self-reported. `retain_unblocked_agents` therefore matches on `origin_agent_id` only. Populate it in the one place that holds the authenticated sender, `cmd::resolve::run`'s cache loop, via `names::insert_with_origin`; plain `names::insert` leaves it NULL and is for locally authored records. NULL is also what pre-006 rows look like, and they are deliberately left unfiltered — a blocked peer cannot be attributed retroactively. Do not start filtering on `by_agent_id`; `a_peer_cannot_hide_behind_an_id_it_wrote_itself` exists to stop exactly that.
- **Never gossip blocks.** They are local policy; a peer learning about them is a privacy leak.
- **Identity comes from the transport, not the envelope.** Blocked-agent matching uses `DirectMessage::sender` / `IncomingEvent::origin`, not the self-reported `from_agent_id` — otherwise blocking is trivially bypassed by editing the envelope.
- **Unblock is not undo.** `block --resource` deletes the local copy by default; `--keep-local` is the escape hatch. Unblocking lifts the row and cannot restore deleted data. Never word a response as though it restored anything.
- **Partial x0x success is reported, not hidden.** `BlockOutcome::x0x_applied` is `None` (not requested), `Some(Ok)` or `Some(Err)`; the local block lands regardless. `av unblock --all` deliberately does **not** lift transport blocks, because it cannot enumerate x0x contacts.
- Agent ids are validated as 64 hex. A mistyped id stored as a block silently never matches anything, which reads as "the block is working".
- **Block policy reads must fail closed.** A `blocks` read that errors is not evidence that nothing is blocked, so `blocks::blocked_ids` propagates instead of returning an empty set, and every caller on a serving path (`search_top_k`, `lookup_name`, both `to_publishable_*` in `cmd/listen.rs`, `cmd/index.rs`, `propagate_resource`) propagates too. `unwrap_or_default()`/`unwrap_or(false)` in any of those is a latent "serve everything the user suppressed" bug — there is a test that drops the `blocks` table to pin this.
- **One block report, read once.** `cmd::block::block_report(conn)` returns the list *and* the per-kind breakdown from a single `list_all`, and both `av block --list` and the web `/api/blocks` call it. They used to each issue their own two queries and build the same JSON by hand — byte-identical, and therefore free to drift — so a block landing between a `COUNT(*)` and a `SELECT` produced a summary whose parts did not add up to its total. Replaying that shape against a concurrent writer disagreed 106/2000 times (~5%), which is why it passed every ordinary run; `the_breakdown_holds_while_another_thread_is_blocking` now asserts the invariant in a loop, and the invariant holds by construction rather than by luck. `blocks::counts_by_kind` is deleted, so there is exactly one way blocks are counted.
- **`blocks.subject_kind` has no CHECK constraint, so it can hold a value `BlockKind` cannot represent.** `BlockEntry` therefore carries `subject_kind_raw` alongside the parsed `subject_kind`, and the report groups and labels on the raw string. Parsing first would file an unrecognised kind under `resource`, and a UI looking up `resource` would find a number that does not include it. Use `subject_kind_raw` to *display* a subject and `subject_kind` to *match* one.
- **Never print an abbreviated id where a block argument is expected.** A block is keyed by *exact* match, so `av search`/`av resolve`/`av block --list` print full ids. Re-introducing `abbrev(&id, 16)` there silently makes the feature unusable. These lines deliberately do **not** print a ready-made `to block: av block --…` command — it was tried and removed as noise; the id plus `av block --help` is the intended path. Peer ids are hidden behind `av search --show-peers` (and always present in `--non-interactive` JSON) because the count is already in the result header and printing every id is unusable at real cluster sizes. `expand_known_prefix` in `cmd/block.rs` additionally refuses a short id that is a strict prefix of a locally-held subject and prints the full id; the `LIKE` there must use two placeholders (`?1` pattern, `?2` exact id) or a full id matches itself and nothing can be blocked at all. An id we do *not* hold is a normal network result, so that case is allowed and only warns. `unblock` checks for an existing exact row *before* the prefix check, or a dead short block left by an earlier build could never be removed except with `--all`.

## Config
- TOML via `AvConfig::from_file(path)`; all fields optional; `validate()` checks ranking weights sum to 1.0 (tolerance 0.01).
- **Two independent weight schemes — don't confuse them.** `AvConfig` defaults (`av-core/src/config.rs`): semantic=0.65, agreement=0.15, feedback=0.10, trust=0.10 (validated). But `av-core/src/constants.rs` has a *different* 5-weight set (semantic=0.55, relevance=0.10, agreement=0.15, feedback=0.10, trust=0.10) used by `av-trust::ranking`. Also name-ranking constants (`NAME_WEIGHT_*`). The constants set is not validated against config.

## Key dependencies & quirks
- `fastembed` v4 with features `["ort-download-binaries", "hf-hub-rustls-tls"]` — declared inline in `av-embed`, not a workspace dep.
- `rusqlite` with `bundled` feature everywhere — every `av-store` connection enables WAL mode, `PRAGMA foreign_keys` **and `PRAGMA busy_timeout=5000`** (see `crates/av-store/src/db.rs`). Declared inline in `av-trust`/`av-query` despite being a workspace dep; depends on same spec. The busy timeout is load-bearing: the web server opens a connection per request and the responder opens its own, so writes overlap, and SQLite's default of 0 turns a momentary overlap into an immediate `SQLITE_BUSY`. For the same reason, anything that reads-then-writes must use `BEGIN IMMEDIATE` (`blocks::delete_resource_cascade_with_names` does it by hand, because rusqlite's `transaction*` methods need `&mut Connection` and these callers hold `&Connection`) — a deferred transaction that upgrades from read to write fails with `SQLITE_BUSY_SNAPSHOT` if anything else committed in between.
- **Two SQLite races that `busy_timeout` does *not* save you from, both fixed in `db.rs` and worth knowing before touching it.** (1) `ALTER TABLE ADD COLUMN` is not idempotent, and `migrate` is reached concurrently by several threads opening a fresh database, so they all see a migration as pending and all run its DDL — the loser died on "duplicate column name". `migrate` now takes `BEGIN IMMEDIATE` and re-checks `applied_migrations` *inside* the write lock, so the loser waits and then sees it recorded; `INSERT OR IGNORE` alone was not enough, and neither was assuming the DDL is idempotent (`CREATE TABLE IF NOT EXISTS` is, `ALTER TABLE` is not). (2) `PRAGMA journal_mode=WAL` needs a lock no other connection will grant and SQLite answers `SQLITE_BUSY` there **without consulting `busy_timeout`**, so a burst of opens made `open` fail intermittently and took the web server down. `ensure_wal` re-reads the mode and accepts the winner's WAL instead, since WAL is a property of the file, not the connection. Note also that `busy_timeout` is per-connection, so it must be the *first* statement in `configure` — anything ordered before it runs with the default of 0.
- `ureq` (sync HTTP) — no tokio or async runtime in the project. The web server is `tiny_http` on plain threads, not an async runtime either.
- `tiny_http` 0.12 — its `unblock()` releases only one waiting thread, so shutdown is polled instead (see Web interface).
- `infer` for MIME detection — `kamadak-exif` for image metadata, `id3` for audio (`av-ingest`).
- `directories` for platform data paths — defined in `av_core::paths`.
