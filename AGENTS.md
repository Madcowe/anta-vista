# Anta-Vista — Agent Guide

## Workspace
- Rust workspace, `resolver = "2"`, **no toolchain file** — build with `stable` (no `rust-toolchain` file pins a version). All crates `edition = "2024"`, version `0.3.0`.
- No `.cargo/config`, no `rustfmt.toml`, no `clippy.toml`.
- **Binary**: `av-cli` publishes the `av` binary (`crates/av-cli/src/main.rs`). All other crates are libraries.
- **Crate dependency graph** (bottom-up, a fan not a chain):
  `av-core` → `av-store`, `av-embed`, `av-ingest`, `av-net-x0x` → `av-trust`, `av-index` → `av-query` → `av-cli`, `av-probe`, `av-test-suite`.
  Note: `av-query` depends only on `av-core`/`av-store`/`av-trust`/`av-net-x0x` — it **bypasses** `av-index`/`av-embed`. Do not add `av-query → av-index` deps without reason.
- `ANTA_VISTA_DB_PATH` env var overrides the default SQLite db path (derived from `directories::ProjectDirs` via `av_core::paths::db_path`).
- `ANTA_VISTA_NO_AUTOSTART` env var (`startup::NO_AUTOSTART_ENV`) makes `startup::ensure_services()` a no-op (reports state, starts nothing). The web test harness sets it so no test spawns a real daemon; it is also an opt-out for users whose x0x is managed elsewhere.

## URI scheme (easy to get wrong)
- Canonical scheme is **`autonomi://`** (flipped from `ant://` in commit `408e97c`, with DB migration `004_canonical_scheme`).
- `ant://` is accepted as an **input alias** only — `av_core::constants::{ANT_SCHEME, AUTONOMI_SCHEME}` and `normalize_scheme()` map `ant` → `autonomi`; indexing/ranking normalize stored targets to `autonomi://`.
- Bare 64-hex strings (no scheme) are auto-prefixed with `autonomi://` (in `av-ingest/src/location.rs` `normalize_uri`).
- New URI-handling code should treat `autonomi` as canonical and normalize aliases early via `av_core` helpers.

## Git
- **Never run `git commit` unless the user asks for that commit in that message.** Finishing a task is not permission to commit. Approval to commit once is not standing approval — a later "remove X and Y" still means edit the working tree and stop, leaving `git status` dirty for review.
- Commit only when the request explicitly names committing ("commit this", "make a commit"), and never bundle unrelated work into a commit just because the tree is already staged.
- `git add`/`git rm` to inspect or stage is fine, but if staging was only for review, say so and leave it staged rather than committing.
- Never `push` without being asked. Both commits in the web-GUI line of work are local only.

## Testing quirks
- **x0x live-daemon tests** (`av-test-suite/tests/x0x_live_daemon.rs`) are `#[ignore]` **and** body-guarded by `skip_if_no_daemon()`. The guard is *discovery-based*, not a health probe: it checks the x0x data dir (`ProjectDirs::from("", "", "x0x")`) for readable `api.port` + `api-token` files. Runs only with `--include-ignored`.
- `skip_if_no_daemon()` / `inject_gossip_payload()` / `spawn_named_instance()` live in `av-test-suite/src/x0x_harness.rs`.
- `av-test-suite` has no `[[test]]` entries in `Cargo.toml` but **does** ship integration tests via auto-discovery (`tests/av_*.rs`, `integration_*.rs`) alongside its shared helpers (`fixtures`, `generators`, `attacks`, `prelude`). Both run under `cargo test -p av-test-suite`.
- Real MiniLM model tests (`--include-ignored`) download ~87 MB on first run via `fastembed`/ORT, cached under the OS cache dir (`av_core::paths::cache_dir`); `FASTEMBED_CACHE_DIR` overrides it.
- **Starter seeding is gated off in tests.** The web harness spawns `av web` with `ANTA_VISTA_NO_SEED=1` (see *Fresh-install starters* under Web interface), because the search tests assert exact result sets on fresh databases. `tests/starter_seed_tests.rs` is its offline suite (baked data, no model, no network); `tests/bake_starters.rs` is `#[ignore]`d — it needs the network and the model because it *regenerates* `src/starters_data.rs`, and a normal `cargo test --workspace` never runs it.
- `proptest` is a workspace dependency — property-based tests exist but are not run as a separate gate.

## CLI
```sh
av <subcommand> [options]
```
Subcommands: `web`, `status`, `resolve <name>`, `search <query>`, `name <uri> <name>`, `index <uri>`, `rate <resource_id> <rating>`, `block`, `unblock`, `purge`, `listen`, `stop`, `propagate <resource_id> <location> <description>`.
Flags: `--non-interactive` (JSON machine mode; may appear before or after subcommand), `--config <path>`, `--timeout <ms>` (default 10000), `--stream`, `-v`/`-vv`.

- **Bare `av`** is now valid: `cli.command` is an `Option<Commands>`, and `None` launches the web interface. `is_offline_command(None)` is true, so bare `av` starts with no x0x installed. Machine mode must still refuse: bare `av --non-interactive` returns `{"ok":false,"error":"no_subcommand"}` with **exit 2** (asserted in `cli_tests.rs`).
- **Startup gating** (`crates/av-cli/src/startup.rs`): `status`, `purge`, `listen`, `stop`, `block` and `unblock` run offline; `resolve`/`search`/`name`/`index`/`rate` require an x0x daemon. In interactive mode the CLI offers to install/start x0x, and `name`/`index` offer the ant CLI + `antd` daemon (port 8082) for `ant://` URIs — keep this flow in mind when touching CLI. `block`/`unblock` are offline because blocking a misbehaving peer has to work when the daemon is unavailable. **The web UI does not gate — it starts.** `startup::ensure_services()` brings an installed-but-down x0x up (never installing), then the listener once x0x answers; `web` (which is an offline command) calls it on boot and `app.js` calls it before every search/index and from the drawer. See *Services lifecycle* under Web interface.
- **Machine-mode** (`--non-interactive`) exits with JSON errors instead of prompting; missing deps are hard errors there.
- **Listener management** (`crates/av-cli/src/listener.rs`): `av listen` writes `<data_dir>/av-listener.pid` (protected by a `PidFileGuard` drop-guard in `cmd/listen.rs` so a crash/timeout rarely leaves a stale PID). `stop_all()` computes every running listener — `/proc` cmdline sweep for `av ... listen` (unix) ∪ PID-file PID — SIGTERM then SIGKILL after ~3s (`--force` skips the grace period), and clears the PID file. `ensure_running()` is called from startup for network commands and by `startup::ensure_services()` for the web UI, and spawns a detached `av listen` from `current_exe` if `is_running()` is false; it only checks aliveness, so an old binary never triggers a respawn by itself — use `av stop` then the next network command to upgrade the responder.

## Web interface
`crates/av-cli/src/web/` + `crates/av-cli/assets/`, served in-process by `tiny_http`. Launched by `av web`, `av gui`, or bare interactive `av`.

- **Reuse the CLI, don't reimplement it.** `web/handlers.rs` calls `cmd::search::collect_results`, `cmd::search::reinforce`, `cmd::rate::record_feedback`, `cmd::rate::is_locally_indexed`, `cmd::index::index_resource` and `cmd::status::database_counts`. If a behaviour changes in `cmd/`, the browser must change with it — extend the shared function rather than adding a web-only copy. `web` deliberately does **not** depend on `av-index`/`av-embed` crates directly.
- **Startup state is a live snapshot, not a boot constant.** `AppState.startup` is an `RwLock<StartupState>`. Search decides whether to fan out to peers from `startup.x0x_config`, so starting a daemon from the setup banner is useless unless `refresh_network_deps()` runs. Every start/install handler calls it. Handlers take one read guard for the whole request rather than re-reading, so a mid-request change cannot alter the fan-out.
- **Services lifecycle: started on demand, stopped momentarily.** `startup::ensure_services()` starts x0x (only when the binary exists and the daemon is not answering) and then the listener (only once x0x answers — a listener with no x0x reaches nobody), returning a `ServiceReport`. It is called from a detached thread right after `av web` binds (binding must not wait on the ~8s start), before every search/index from `app.js`, and by the drawer's Start buttons via `POST /api/services/ensure`. `AppState.services_lock` (a `Mutex<()>`) serialises these so a boot start, a search and a click cannot all spawn `x0x start`; the loser waits and then finds the services up. `POST /api/deps/x0x/stop` is **momentary** — the next search/index undoes it — so there is no sticky "stopped" flag. The setup banner is **install-only** (`needs_install: !x0x_installed`): a crashed or manually stopped service is restarted, not advertised, so it can never re-raise the banner. `app.js` keeps the last `/api/deps` payload as `lastDeps` so `ensureServices()` only shows `Starting x0x…` when the cached state says x0x is down (a service that died in the last 15s is restarted silently — this is a start, not a health check). `ANTA_VISTA_NO_AUTOSTART` makes `ensure_services` a no-op; the web test harness sets it so no test spawns a real daemon. Pinned by `ensure_services_reports_the_services_it_looked_at`, `the_drawer_has_start_and_stop_for_both_services`, `the_setup_banner_is_for_installs_only` and `search_and_index_ensure_the_services_first`.
- **A second `av web` (or second double-click of the binary) reuses the first instead of dying on the port.** The browser's close button does not stop the server, so the natural second start used to fail at the bind — with the error printed where an icon launch has nowhere to print it, so the page never opened ("the icon works once, then is unresponsive") — and every later terminal start got `EADDRINUSE` against a perfectly healthy instance. `web::run` now downcasts the boxed tiny_http error to `AddrInUse` and probes the busy port for `GET /api/ping` (`{"ok":true,"service":"anta-vista","version":…}` — no DB, no dep probe, the cheapest route here); when the squatter answers as us it prints `already running at {url}`, opens it unless `--no-open`, and exits 0. A foreign *or hung* occupant still gets the bind error — a hung one answers nothing within the 800 ms probe timeout, and "reusing" it would open a tab that cannot work. Note this happens *after* the DB pre-warm, like every other part of boot; the probe is what makes the conflict cheap, not the bind order. Pinned by `the_ping_endpoint_identifies_the_server`, `a_second_web_on_a_busy_port_reuses_the_running_server` and `a_foreign_listener_on_the_port_is_not_mistaken_for_av`.
- **A dead tab notices, and comes back on its own.** The page is served by the very server it polls, so a rejected `fetch` on loopback means that server is gone — there is no transient network in between. `api()` therefore calls `noteServerDown()` on a fetch rejection, so any user action that hits a dead server raises the banner at once rather than up to 15 s later. That shows `#server-banner` — deliberately *not* the setup banner, whose install-only meaning is pinned — saying the server looks stopped, that restarting it on this address makes the page reconnect by itself, plus a Check now button. The old `setInterval(refreshDeps, 15000)` became a chained `setTimeout` whose delay is `serverDown ? 3s : 15s`, which is what makes the reconnect prompt; the next successful poll calls `noteServerUp()` and takes the banner down. Nothing in a page can start a process, so the banner never pretends to offer one. Pinned by `the_dead_tab_banner_reconnects_on_its_own`.
- **Fresh-install starters arrive baked, not fetched.** `https://autonomi.com/`, `https://x0x.md/` and `autonomi://711c7e20006ff3e0ac6c1f3063286a0c1a3e4c409642e8c526173fa60bb7078a/lucky.jpg` (tag `dog`) ship as **pre-computed rows — descriptors *and* their MiniLM vectors — in `crates/av-cli/src/starters_data.rs`**, so `starters::ensure_seeded` at `av web` boot (synchronous, after the migration pre-warm and before bind) is a few local INSERTs: no network, no model load, and the status drawer already reports `Resources: 3` at first paint. The file is **generated** by the `#[ignore]`d `tests/bake_starters.rs` (`cargo test -p av-cli --test bake_starters -- --ignored --nocapture`) — it fetches the two pages, builds the Autonomi descriptor from the location + tag alone (content-immutable address, and no antd/ant backend exists on a fresh install — never fetch it at seed time either), embeds all three and rewrites the file; regenerate rather than hand-editing, and commit the result. Ordering rules, each user-visible: a `starter_seeds` row (migration `008_starter_seeds`, `av_store::repo::starter_seeds`) settles a location forever, so **a purged starter stays purged** across restarts; a location that already holds a resource is *adopted* untouched (the user's own copy wins); a blocked content hash skips the write **and stays unmarked**, so `av unblock` can still admit it later (block reads fail closed and abort the pass); any error warns and gives up rather than blocking boot. `ANTA_VISTA_NO_SEED=1`/`true`/`yes` disables it; scoped to `av web` only — the default bare-`av` launch. Pinned by `a_fresh_web_install_ships_with_the_starter_resources` (the one server spawned with seeding on) and the offline `starter_seed_tests.rs`.
- **`miniLM` loads lazily** (`EmbeddingCache(OnceLock<Result<Arc<MiniLmProvider>, String>>)`) — binding the socket must not wait on an ~87 MB model. Success *and* failure are cached so a broken cache isn't retried per keystroke.
- **Per-request `av_store::open()`** is required (`Connection` isn't `Sync`). This is why `av-store`'s migration bookkeeping uses `INSERT OR IGNORE`: several threads can reach a fresh database at once, all see the migrations as pending, and all of the DDL is idempotent. `web/mod.rs` also pre-warms the database before binding so the race is not hit in practice. Covered by `test_concurrent_opens_of_a_fresh_database` in `av-store/tests/on_disk.rs`.
- **Shutdown is a poll, not `Server::unblock()`.** `tiny_http::Server::unblock()` releases exactly **one** waiting thread ("If there are several such threads, only one is unblocked"), so a 4-worker pool would hang on `--run-for`. Workers use `recv_timeout(200ms)` against an `AtomicBool` instead.
- **Host-header guard** rejects anything that isn't a loopback name, which is the DNS-rebinding defence for a loopback-bound server. Keep it in front of every route.
- **`hidden` is how this UI shows and hides things, and an author `display` rule defeats it.** The browser's `[hidden] { display: none }` lives in the *user-agent* stylesheet, so any author rule that sets `display` silently outranks it — no specificity contest to notice, because the losing rule is in a different origin's stylesheet. `.drawer` and `.banner` are both `display: flex`, which made the status drawer and the setup banner painted from first paint, and made the drawer's close button set `hidden = true` and visibly do nothing: a dead-looking × that was working correctly. The `[hidden] { display: none !important; }` guard at the top of `modern.css` is load-bearing, not decoration — it has to be `!important` to beat a same-origin author rule. It covers retro.css too (which sets no `display` on either panel) because it is unguarded by theme. If you add a `display` rule to anything `app.js` toggles, the guard is what saves you; do not remove it. `hidden_wins_over_the_layout_rules_of_the_panels_it_hides` pins both halves — the guard, and that `.drawer`/`.banner` are still `display: flex` so the guard stays necessary.
- **The 90s are the default, and the toggle's label names what is on screen.** Default is `retro` in three places that must agree — `<html data-theme="retro">`, *both* boot-script fallbacks (an unreadable stored value, and storage being unavailable at all) and `applyTheme`'s `||` fallback — because a disagreement boots a hardened browser into one theme while the markup says the other. The label rule is: it names the current theme and clicking *leaves* it (`retro` → "I don't like the 90's", `modern` → "I don't like now"). It used to be inverted — "I don't like the 90's" while pointing *at* the 90s, and clicking then went to them — so on the default the button read as an escape that went the other way. The string exists twice, in `render.rs` markup (pre-JS, so the header cannot flash a wrong label) and in `applyTheme`, and the two must match; the `app.js` comment describing it as "what the button will switch *to*" was what made the inversion look deliberate. Related: `retro.css` recolours the shell but does not lay it out — `.bar`/`.drawer`/`.banner` take their `display` from `modern.css`'s **unscoped** structural rules, so scoping `modern.css` under `[data-theme="modern"]` to tidy the cascade would render the default's shell unstyled. Related: `retro.js` inserts `#retro-marquee` *before* `#results-count` inside the same `<h2>` — a second `aria-hidden` copy of the count, which is the point — so it has to be taken down again when the theme leaves retro, or modern shows the count twice as a stray unstyled line beside the heading. Its theme observer therefore installs **and** uninstalls (and disconnects the per-banner observer it holds, or the detached track keeps waking it). Pinned by `the_90s_are_the_default_theme_and_both_bootstrap_fallbacks_agree`, `the_theme_button_describes_the_theme_it_is_showing_not_the_one_it_opens` and `the_static_label_matches_the_default_so_the_header_does_not_flash_a_wrong_one` and `the_scroll_banner_does_not_outlive_the_theme_that_gives_it_a_reason_to_exist`.
- **The wordmark is two logo images, and CSS picks the theme's copy — not `app.js`.** `<h1 class="wordmark">` holds `img.wordmark-retro` (`/assets/wordmark-retro.jpeg` — the 90s badge) and `img.wordmark-modern` (`/assets/wordmark-modern.jpeg` — the synthwave strip); `modern.css` sizes both from one **unscoped** `.wordmark img { width: 26rem; height: auto }` (4× the ~6rem text it replaced — the logo is deliberately the masthead, and this one number is the size knob) and hides the badge, and `retro.css` re-shows it **and scales it to ~80% of the shared width** (21rem vs 26rem — same rule, one `width` declaration) with a `[data-theme="retro"]` selector — the attribute raises specificity, so the show *and* the scale win over modern.css regardless of load order (retro.css loads first, modern.css second), and scoping the *sizing* into a theme selector would break the default theme, because retro recolours but does not lay out. The pick is CSS rather than a JS `src` swap because the boot script has already set `data-theme` in `<head>` before the body paints, so the right logo is on screen in the first frame with no script of ours — the same reason the static theme label exists. Each `<img>` carries `alt="Anta-Vista"` (only one copy is ever displayed; `display:none` takes the other out of the accessibility tree, so the name is announced once, and a failed image falls back to the same visible text) plus real `width`/`height` attributes, which is what lets `height: auto` preserve each logo's own aspect ratio — they are the source files' actual pixels. The files live in `crates/av-cli/assets/` and are `include_bytes!`ed, so a rename is a build error rather than a silent 404. Sizing and swapping in one value each; if a logo looks wrong, that is the knob. Related: the modern accent is purple from the same family as the synthwave logo's background (`#1f1b52`, sampled from the JPEG): **one value**, `--accent: #7a6ee8`, everywhere it appears — primary button (dark `--accent-fg: #140a2e` on it, 4.7:1), badge tint, link/title hover (4.7:1 against `--bg`; AA floors its luminance at ~0.20, the raw sample would be ~1.4:1 there). A darker two-value split (`--accent-surface` with light text) was tried and reverted on request — do not reintroduce a second accent var, do not "restore the blue", and do not darken `--accent` below its hover floor without re-checking that contrast. Pinned by `the_wordmark_is_a_theme_swapped_logo_with_the_name_in_alt_text` and `css_picks_the_theme_logo_and_keeps_its_aspect_ratio`.
- **The status trigger is a toggle, and the drawer must leave room to be dismissed.** `setStatusOpen` owns the state; the trigger derives the next state from `ui.statusDrawer.hidden` and its label and `aria-expanded` both follow, so it reads correctly while collapsed. The drawer is capped at `min(26rem, calc(100vw - 3rem))`: at `26rem` it is wider than a phone viewport, and full-bleed meant it covered the header, so the trigger was underneath it too and the overlay click-out was unreachable — the only way out was the ×. `.drawer-head`/`.drawer-foot` are `flex: 0 0 auto` because `.drawer-body` is `flex: 1` (basis 0, so it contributes nothing to shrink) and would otherwise leave the header absorbing all the shrink, clipping the close button on a short viewport with a long status list.
- **Assert on CSS with `css_rule`, not `contains`.** `modern.css` carries comments that name the very selectors a test looks for, so a `contains` or a fixed character window around a match starts passing for the wrong reason. `css_rule` strips comments and matches whole selectors. `css_rule_lookup_finds_a_rule_and_ignores_prose` guards the helper itself.
- **Test harness quirks** (`crates/av-cli/tests/web_tests.rs`): reads the child's stdout **byte at a time** and only parses port numbers out of *complete* lines — reading a byte at a time and testing after each one parses the half-arrived `"8787"` as `87`. stderr is drained on a background thread (an undrained pipe fills and blocks the child, and hides why a server died). `connect` retries. Tests must not assume the host lacks `x0x`/`ant`; the Autonomi tests assert the invariant that holds either way.
- **The web `/api/block` cannot escalate to x0x at all.** It rejects a caller-supplied `x0x` field with a 400 rather than ignoring it, because a loopback server is reachable by any page the user has open. `av block --agent <id> --x0x` is the only route. Warning text comes from `cmd::block::warning_for` so browser and terminal cannot drift.
- **UI honesty rules.** Repeatable-but-true warnings ("peers do not consume feedback yet") are shown and offer "don't show again" (`anta-vista-muted-warnings` in `localStorage`, keyed by the server's `warning_id` — a *different* warning still gets through). Install commands come from the **server** (`ant_install_command()` / `x0x_install_command()`, both overridable for tests via `ANTA_VISTA_ANT_INSTALL_CMD` / `ANTA_VISTA_X0X_INSTALL_CMD`) and travel with the error, so the page never hardcodes a POSIX command and shows the wrong one on Windows. `/api/download` is a **real daemon fetch**, not a stub: it returns bytes with the shared MIME policy, `502 download_failed` when the fetch fails, and `503 no_download_backend` (carrying the install command) when neither antd nor the ant CLI exists. See *Autonomi in the browser* below.
- **The install dialog stays open through the run, and reports the outcome inside itself.** The Run button is `type="button"` — a `method="dialog"` form closes on submit, so the old flow closed the dialog *before* the install POST ran and then wrote the result into `ui.banner`, which the next `refreshDeps()` wiped (`ui.banner.replaceChildren()`), making a successful install look like nothing happened. The click handler now posts while the dialog is open, then sets the title, `#install-hint` and `#install-output` (the installer's log, capped at 8 KB server-side) in place; `refreshDeps()` runs only on `close`, and only when a run actually happened (`ui.dialog.dataset.ran === '1'`). A successful x0x install also calls `ensureServices()` so the daemon comes up without a second click. `openInstall` fully resets the dialog (hint, log, Run label/disabled) so a previous run never bleeds into the next one. Pinned by `the_install_dialog_stays_open_and_reports_the_outcome_in_place`.
- **An install that an index asked for owes the user that index back.** `no_download_backend` fires from the shared `runIndex(uri, tags)` (extracted from the Add a Link submit handler — both paths take the same route, and no `requestSubmit`, which is pinned out of this file) and passes `{ uri, tags } to openInstall` as a `pending` argument; the button menu then gains **Index link** (`#install-index`) on ant-install success, which closes the dialog and resumes `runIndex` with the saved link — stranding the user at a lone Cancel after installing would otherwise mean retyping the URL. The dismiss button (`#install-close`) is only "Cancel" during consent: after any run (success *or* failure) its label becomes "Close", because it no longer cancels anything. `openInstall` restores "Cancel" and hides Index link for the next open; the button is never offered for x0x installs or an ant install with nothing pending. Pinned by `an_install_triggered_by_an_index_offers_to_finish_that_index`.
- **An install endpoint's `ok` is transport-level; the truth is in `installed`/`running`/`log`/`hint`.** `POST /api/deps/{x0x,ant}/install` always answers `ok: true` when the request itself ran — a third-party installer failing is not an HTTP error, and the old `ok: false` made the browser's `api()` throw a meaningless `Error("200 OK")`. The response carries `installed` (post-verified by re-running the binary's `--version` check), `running` (x0x only: a live daemon ping), `already_installed`, `command`, `log` (combined stdout/stderr, capped) and `hint`: "exited successfully/failed without leaving a working binary" when verification fails, "installed but the daemon is not answering" when the binary is there and the ping is not, and the PATH advice (`export PATH="$HOME/.local/bin:$PATH"`) on a fully successful Unix install — because both upstream installers drop into `~/.local/bin`, which is on a login shell's PATH on some distributions and not others (the Porteus case). `x0x_binary_available` / `ant_cli_binary_available` / the start/stop chains / `download_via_ant_cli` all resolve through one pure helper, `resolve_bin(exe, path_string, sep, candidates)` (`x0x_resolve_path` / `ant_resolve_path`), which prefers a PATH hit and falls back to the installer's home directory — detection and use must agree, or a binary found only in `~/.local/bin` is reported as installed and then fails to spawn. The old `refresh_ant_path` (`unsafe { set_var }` from web request threads, Windows-only `;` separator) is gone. Pinned by `resolve_bin_*`, `cap_install_log_*` and `run_installer_*` in `startup.rs`, and the `install_*` family in `web_tests.rs` (which drive stub installers through the env seam inside a temp HOME, never the network).
- **"Add a Link" reports through one dismissible dialog, and closing it shows the row.** The old `#add-status` paragraph was a single line that scrolled away as stages were appended, and it was easy to miss entirely — the ingestion sequence is now `#index-progress-dialog`, a `<pre>` in a `method="dialog"` form, so it waits for the user rather than vanishing. Three rules keep it legible: stages **append** a line (`indexProgressLine`); byte progress **replaces one line** (`setIndexProgressLive`, because the SDK reports many times a second and appending would fill the log and evict the stages); and `showModal()` is called from exactly one guarded site (`openIndexProgress`) — calling it on an already-open dialog throws `InvalidStateError`, which is how the browser route broke while both the fetcher and the submit handler opened it. The outcome is stashed by `finishIndex` and flushed by the dialog's `close` event into `renderIndexedResult`, which **replaces** the results list with the one indexed row (`source: 'local'`, no score — `renderResult` hides the score element when `result.score == null`, because "score 0.000" for an item that has never been ranked is a lie). An early Esc-dismiss still flushes on completion: the result must not depend on the user's patience — but only while the results area still belongs to that index: `resultsEpoch` is bumped by every search (on submit *and* on render) and recorded as `indexEpoch` when the index starts, and a flush whose epoch no longer matches yields the screen, because a late row plus "this is the resource you just indexed" over live search results is a lie. The live helper must also pop the trailing `''` from the buffer's final `'\n'` *before* popping the live line — popping the wrong one glues every update onto the last and the log reads "Fetching…Fetching…Fetching…". The success branch also ends on a short `Resource: <location> has been indexed.` line, preceded by a blank line so it does not read as the tail of the paragraph above it, because the `Added "<description>"` line above it can be 800 characters of the document's own text and the log is scrolled to its bottom — without it the last thing on screen is a wall you must scroll up from. Duplicates and errors render nothing. `no_download_backend` closes the progress dialog before `openInstall`, so two modal dialogs never nest. The retro terminal styling is scoped `[data-theme="retro"] .progress-output` — unscoped it would load after `modern.css` and win in the modern theme. Pinned by `the_index_dialog_is_the_only_index_output`, `byte_progress_replaces_one_line_and_stages_append`, `showModal_is_guarded_so_a_dialog_cannot_be_opened_twice`, `closing_the_index_dialog_shows_the_indexed_resource`, `the_index_dialog_ends_on_a_short_line_naming_the_resource`, `a_search_that_lands_during_an_index_keeps_its_results` and `the_retro_progress_terminal_is_theme_scoped`.
- **A result row leads with its identifier; the description goes underneath, in both the CLI and the browser.** `av search` prints `location` then an indented `description`, and the browser now matches it for every source. Do not branch row layout on the location's *scheme*: that is what made `http(s)` results use `description` as their link text (hiding the URL entirely) while Autonomi results showed the location, so the same field rendered two ways. `source: "name"` inverts deliberately — the name is the heading and the location is the target it resolves to, which is why `cmd/search.rs` prints it `name → target`. `result.description` is the text anta-vista **embeds**, so for a text or PDF document it is up to 800 characters of the file's own content (`synthesize` in `av-ingest/src/describe.rs`); it must never be a heading or a dialog sentence. The remove confirm names the resource by `result.location` for the same reason.
- **A row spins while an open is in flight; a status line alone can sit still for seconds.** `.row-spin` sits in the `result-template` before `fetch-status` (`aria-hidden` — the status line carries the meaning; it starts `hidden`, so the global `[hidden]` guard is what keeps the rule's own `display` from painting it), with an unscoped `modern.css` rule (`display: inline-block` + `av-row-spin` — unscoped because retro recolours but does not lay out). Shown and hidden from **exactly one site each**, both in `openView`: `inFlight` already means "an open is running", so a repeat click returns the same promise and cannot double-toggle it, and the hide lives in the same `.finally` that clears `inFlight`. Deliberately *not* `setBusy`, which blinks off during the plan phase while the wait is far from over. The file's global `* { animation: none !important }` reduced-motion rule stops it already — do not add a second block. Pinned by `the_row_spinner_marks_a_fetch_that_has_not_landed_yet`.
- **Result actions are Recommend / Remove / Block, and the last two are not the same verb.** "Recommend" posts `rating: "useful"` (the value is unchanged; only the label is) and is the *only* action that can share a link, so it confirms first for `source: "network"` and does not for `source: "local"`. No/Escape must be a complete no-op — no request, no disabled buttons, no status. "Remove from local index" is `POST /api/purge` → `cmd::purge::purge_resource`, which frees local rows and writes **no block**, so a peer can return the link; it is offered only for `source: "local"`. "Block" is the durable one. Never word Remove as though it stopped the link arriving, and never word Block as though it restored anything.
- **Removing or blocking a result must not re-run the search.** Both use `dropResult`/`dropResultsFromAgent` in `app.js` and report through `#results-note`, which lives outside the rows because the row takes its own status line with it. The three `ui.form.requestSubmit()` calls that used to be there re-queried the network — which is a second chance for a peer to hand straight back the link the user just removed. A test asserts `requestSubmit` stays out of `app.js`.
- **The "Autonomi only" checkbox filters the rows already on screen; it does not re-query.** Each result row carries its location (`node.dataset.location`, stamped in `renderResult`), and the checkbox's `change` handler calls `applySchemeFilter()` (app.js), which derives the scheme client-side via `locationScheme()` — bare 64-hex is autonomi, `ant://` normalises, undecidable fails closed, exactly like the server — then hides or reveals rows in place and recounts. A re-query would be slow *and* second-chance results the user just removed. The fresh-search path is unchanged: `runSearch` still appends `&scheme=autonomi` when checked, so peers filter early and the server re-filters on receipt. Two exemptions matter: the "just indexed" row is marked `data-from-index` and is never hidden (it reports an action the user just took, not a search result — hiding it would read as the index having failed), and flipping the toggle during an in-flight search does nothing visible (the rows arrive already filtered by the request's checkbox state — `renderResults` re-applies the filter anyway for a mid-flight flip). `recountResults` counts *visible* rows (hidden rows are still DOM children), and when everything is filtered out it says "No results" rather than "Nothing left", because the rows are still there — they just don't match. The preference persists as `anta-vista-autonomi-only` in `localStorage` (theme-style try/catch — an unavailable store means the filter starts off). The `.search-block` wrapper in `render.rs` (form + checkbox) and its two `modern.css` rules are unscoped on purpose: retro.css recolours but does not lay out, so scoping them would break the default theme. The Rust-side behaviour lives under the fan-out bullet below. Pinned by `the_search_form_offers_the_autonomi_only_filter` and `flipping_the_autonomi_toggle_filters_the_shown_rows_without_a_new_search`.
- **An agent block is not a disconnect, and the peer dialog has to say so.** An agent block drops the peer's search responses *and* the names it published, but it does not disconnect it — `av block --agent <id> --x0x` is the transport route, and the dialog only offers that command to run, because the loopback `/api/block` cannot escalate. The dialog also says indexed links stay and the block is reversible with `av unblock`. It uses `#peer-block-blurb { white-space: pre-line }` for the command block. **Do not reintroduce the old claim that "names this peer has already published still resolve, because those are stored locally"** — it was true while an agent block only filtered search responses, and became false once name records carried a transport origin. `web_tests.rs` asserts the phrasing is absent. Do not add x0x escalation here, and do not pad the dialog back out with limits the code now enforces itself.
- **Known gaps to keep in mind:** search blocks (SSE is the follow-up); peers do not consume `av.feedback.v1`, `av.claim.v1` or `av.presence.v1` messages, so a broadcast rating changes nobody's ranking. Nothing ever *emits* an `av.claim.v1` either: the `claims` table, `ClaimPayload`, `MessageKind::Claim` and `TOPIC_CLAIM` all exist and the responder subscribes, but there is no `publish_claim` and no receive arm, so `claims` is always empty and the 0.15 `agreement` weight in `av-trust::ranking` is a constant 0.5 that cannot reorder results. Do not treat agreement as a live ranking signal, and do not add a claim producer without solving the Sybil problem first — `docs/follow-ups.md` has the write-up and a user-mediated replacement; `NameRecord`s cannot receive feedback because `feedback_events.resource_id` references `resources(id)`.

- **Search/resolve fan-out** (`crates/av-cli/src/network.rs`): queries go out BOTH as direct messages AND as a gossip broadcast. Direct fan-out candidates = recent `peer_cache` entries ∪ x0x-discovered agents (`/agents/discovered`, `/presence/online` via `X0xNetClient::discover_agent_ids`), deduped, self excluded — so peers never contacted before (and online-only peers) are still queried. Direct queries are sent from detached threads per candidate, each with its own `query_id` registered **before** the send, and `send_direct` permits slow relay/`gossip_inbox` routing (90 s HTTP timeout) — a past bug gated sends on a 2 s `connect_agent`, silently dropping every relay-routed peer. Responses match by any issued `query_id` (direct ids differ from the gossip id). Direct messaging is the fast path; gossip is mesh-driven and slower.
- **The scheme filter is normalised once in `collect_results` and re-enforced on receipt.** `av search --scheme ant`, `?scheme=ant` and the browser's "Autonomi only" checkbox all pass through `av_core::types::normalize_scheme` at the top of `collect_results` (`cmd/search.rs`) before reaching the local `SchemeFilter`, the name filter, and the `allowed_schemes` on the wire — stored `location_scheme` is canonical `autonomi`, so filtering on the raw alias matched nothing. The wire filter is **advisory**: an old or hostile peer may ignore it, so `execute_search` (`network.rs`) re-filters every response's results on arrival — before the push, before `--stream` prints — deriving the scheme from `location` via `analyze_location` (bare 64-hex and `ant://` both normalise; an undecidable scheme fails closed) rather than trusting the peer's self-reported `location_scheme`. Never "simplify" this to trusting the request. Pinned by `an_autonomi_filter_*`/`an_undecidable_scheme_fails_closed` in `network.rs` and `the_scheme_filter_separates_autonomi_from_http_results` (which also pins the `ant` alias) in `web_tests.rs`.

## Autonomi in the browser
`crates/av-cli/src/web/viewer.rs`, the vendored SDK, and the `av web` assets. The browser fetches Autonomi records itself over WebRTC, so an Autonomi link can be viewed and indexed with **nothing installed** — no `ant` CLI, no `antd`. The daemon path remains, explicitly, as a fallback.

- **Cache the vendored SDK hard; never cache our own assets.** These are opposite trades and both are deliberate. `SDK_BASE` carries the version, so nothing under it can change meaning in place and `vendor_asset` serves `public, max-age=31536000, immutable` — which matters far more than the bytes it saves, because 5.4 MB of the 5.6 MB is `ant_core_bg.wasm` and browsers cache *compiled* WASM per URL. Without it the compile is redone on every load, and two tabs opening at once compete for the same CPU doing it twice. `/assets/app.js` and the CSS go through `own_asset` and keep `no-store`, because they are compiled into the binary and a cached copy produces a UI that quietly behaves in a way the current code no longer explains — the server is never wrong and nothing admits to being out of date. `the_vendored_sdk_is_cacheable_because_its_url_carries_the_version` pins both halves, because the failure is silent in both directions.
- **Warm the SDK on hover or focus, not on click.** Compiling and instantiating 5.4 MB of WASM is the longest single stretch of a first fetch — and that compile happens *inside* `AutonomiClient.connect`, along with the seed dial and authentication, so warming only `loadSdk()` (which merely imports the package) left every click paying both. The warm therefore starts `loadSdk()` *and* the shared `getSharedClient()` connect, so a click lands on a client that is already up and pays only the DataMap lookup. Hovering or tabbing onto a `.result-loc` is free intent that arrives first; both promises are cached (`loadSdk` including its failure, `getSharedClient` by clearing its slot), so warming costs nothing if the click never comes and duplicates nothing when it does. A phone fires no `pointerenter`, so `focus` is wired too. Pinned by `hovering_an_autonomi_location_starts_the_wasm_compile_before_the_click`.
- **The SDK is vendored, pinned and MIT/Apache-2.0.** `assets/vendor/ant-browser-sdk/0.1.2/` holds the **complete reachable import graph — all 26 files**, ~5.6 MB, dominated by the 5.4 MB `wasm/ant_core_bg.wasm` (0.1.2 is 0.1.1 plus upstream's WebKit connection fixes — only the two `wasm/` files differ). It is vendored whole on purpose: a hand-trimmed subset looks like dead weight until a dynamic import inside a worker resolves a file that was dropped. `.map`/`.d.ts` are excluded. `SDK_VERSION` in `render.rs` is the single pin. Each file needs an `include_bytes!` arm in `render.rs` and is served at `SDK_BASE` (`/assets/vendor/autonomi-sdk/0.1.2/`) — note the runtime prefix is *not* the directory name. `the_vendored_sdk_is_served_with_types_the_browser_accepts` pins the WASM MIME (`application/wasm`; `application/octet-stream` fails to stream-compile) and that the page's boot global matches the served path.
- **An Autonomi location is openable, so it must look and behave openable.** `.result-loc` used to carry `cursor: help` plus a comment claiming an Autonomi location had "no open/download path yet" — which by then was false. It underlined on hover, showed a question-mark cursor, and did nothing when clicked, which reads as broken rather than as a deliberate choice. It is now a `<span>` (never an `autonomi://` href) that app.js wires a click and a key handler on, marks `is-openable`, and gives `role="button"` + `tabindex="0"`. **Set the class, the role, the tabindex and the handlers together in `wireFetch`** — that is the one place that decides the element is openable, and splitting the affordance from the handler is how the two drifted apart. The CSS keeps the inert state and the openable state distinct in *both* themes (`modern.css` and `retro.css`), because a link-shaped element that underlines and lies is worse than one that looks plainly inert. It also *hovers* like the link it stands in for: `.result-loc.is-openable:hover` takes `.result-title:hover`'s colour in each theme (accent in modern, red in retro), because an http row's heading is a real `<a>` while an Autonomi row's is this span, and the two layouts must not advertise clickability differently — the non-openable location is deliberately left out of the rule. **There are no Open/Save buttons in the row** — the location is the only open path (one click opens what the browser can show and downloads what it cannot), the outcome lands on the row's `fetch-status` line (`Opened …` / `Downloaded as …`), and the fetch group holds nothing but Stop, revealed only while a fetch runs. A stop is recognised by **our own `controller.signal`**, never by the SDK's error wording: any error thrown while the signal is aborted is recast as `DownloadCancelled` in `runOpen`'s catch (the recast used to live in `obtain`, which was folded into `runOpen` when the open path learned to stream — the guard moved, it did not weaken), because every *other* error is what routes a failed fetch to the daemon fallback — an abort left untranslated made Stop start a second, unstoppable download. Pinned by `an_autonomi_location_looks_clickable_because_it_is` and `stopping_a_browser_fetch_never_falls_back_to_the_daemon`.
- **Never upload a file to learn its name.** `POST /api/view/plan` takes the URI, an optional `X-Anta-Mime` hint, and **at most a 16 KB prefix** of the bytes (`blob.slice(0, PLAN_PREFIX)` against the server's `PLAN_PREFIX_CAP`, refused over — never clamped, per the `MAX_BODY` rule), and answers `{filename, renderable, mime_type}`. Both the download-on-click and the oversize branch of open use it. This exists because both used to `POST /api/view/blob` purely to read a filename back, which meant a 64 MB record — fetched successfully — then failed with `request body is larger than the 33554432 byte limit`. That is a confusing error for a successful fetch, and `indexAutonomiInBrowser` already avoided it by checking size *before* uploading. The prefix exists because the SDK reports `application/octet-stream` for most records, so a hint-only plan cannot tell a JPEG from a blob. `opening_severs_the_opener_and_saving_never_uploads_the_file` pins that the download path never routes the file through `postBlob` (exactly one whole-file upload exists — opening a displayable copy; two call sites since the reopen and fresh paths each have one) and that `postPlan` slices rather than sending the whole blob; `the_client_and_server_agree_on_the_prefix_cap` pins the two constants against each other, since they live in two languages.
- **A save streams to disk through a service worker; the page never holds the file.** When the plan says the file cannot be shown (or is over the viewer cap), `runOpen` starts a worker download instead of buffering: `ensureWorkerControlAtBoot` runs at page boot and `ensureServiceWorker` on demand, both registering `/autonomi-stream-sw.js` (served `own_asset`, `no-store` — a cached worker keeps running yesterday's code), the page mints a one-shot token, posts `{type:'av-download', token, filename, mime, size}` plus a `MessagePort`, and anchors a `download`-attribute navigation at `/av-download/<token>`. The worker answers that URL with a pull-fed `ReadableStream` (`attachment`, `nosniff`, `no-store`), one chunk per `pull` so a slow disk pauses the WebRTC read — and a token it does not know gets an empty 404 **inside the worker**: falling through to the server would save the error page's bytes as the file, because of that `download` attribute. `pipeReaderToPort` speaks the protocol; `cancelled` (the user dropped the download in the browser's own UI) is recast as `DownloadCancelled` — a stop, never a daemon fallback. **No worker** (no service-worker support, or the registration was refused) returns null and the caller buffers exactly as before, so the old flow is the fallback, not a rewrite of it. The token is carried in the URL because `window.open` must happen synchronously on the click — a picker cannot be awaited in the same gesture (`showSaveFilePicker` requires transient activation and Chromium consumes it on `window.open`; only Chromium has the API at all), which is why the download lands in the browser's Downloads as it always did. The size travels with the token and becomes the response's `Content-Length` (`-1`/absent = unknown, never a wrong length): the browser's download UI then shows a total instead of an anonymous crawl, and a body stopping short fails loudly rather than leaving a silent hole. **Firefox terminates a service worker idle for ~30 seconds — even one mid-save** (StreamSaver's README states the timeout; immich #21490 reproduces it), and the dead worker takes the response body with it, which Firefox reports as a `.part` file whose "source file could not be read" — a message that reads as a broken file, not a killed worker. Chrome counts an open response body as activity, which is why the failure looks Firefox-only. The page therefore **pings the worker** (`av-ping`, every 10 s via `keepaliveAdd`/`keepaliveRemove`, reasoned sets because a save and a playing session overlap) for the life of every download *and* every open player session — a session's taught MIME dies with the worker too, so teardown (`teardownPlayer`) must release its reason. Related: the player's Save **opens the file before starting the download** — a `.part` that receives nothing for the seconds a lookup takes is exactly the silence the idle clock kills, and a failed open must start no download at all; its no-worker fallback drains the reader already open rather than re-fetching. **A page must be *controlled*, not merely registered** — a save without a controller silently degrades to the buffered path, and the media route (below) refuses outright — and `clients.claim()` is known to skip the very document that called `register()`, the browser's and the SDK's shared remedy being a single reload. `ensureWorkerControlAtBoot` (called from the boot section, before anything can need the worker) therefore does nothing on an already-controlled page, but on an uncontrolled one registers, gives claim its chance, and `location.reload()`s only when the controller still has not arrived — after which the active worker controls the page at load, the ordinary way. The `anta-vista-sw-reloaded` flag lives in sessionStorage (per tab) and is set before the async work, so a profile where control never lands loops at most once, and storage that refuses the flag means no reload at all. Pinned by `the_page_makes_itself_controlled_by_the_worker_before_anything_needs_it`. Pinned by `the_streaming_service_worker_is_served_as_a_script_it_can_register`, the streamed-region half of `opening_severs_the_opener_and_saving_never_uploads_the_file`, `the_worker_is_kept_awake_for_the_whole_length_of_a_transfer`, `the_media_save_opens_the_file_before_it_starts_the_download` and `the_download_declares_the_length_the_datamap_already_knows`.
- **Audio and video play inline, streamed by the same worker, and the media route is patched.** The plan's `audio/*`/`video/*` verdict routes the open to `#media-dialog` (a **non-modal** dialog — listen while browsing, and a modal would hide the row's own Block button while its file plays; `closePlayerIf` closes it when that row is blocked or removed). A row that says so from the start also opens **no progress tab** — the phases land on the row's status line and the dialog appears when ready (the `likelyMedia` exception under *window.open* below). Playback goes through `client.createMediaSource(address, {serviceWorkerUrl: STREAM_SW_URL})` — the SDK's MediaBridge, whose random-access reader keeps playback off the page's memory, capped at `MEDIA_MAX_BYTES` (1 GB, the SDK's own limit; past it, or with no worker, the file falls through to the save/viewer as before). `startPlayer` takes its client from `getSharedClient` and applies the same invalidate-and-retry-once as `openAutonomi`, because `createMediaSource` is a *second* network reader — random access, a different wasm path from the sequential open that already fetched the plan's prefix — and one transient lookup failure here used to surrender the whole route: a 52 MB video fell through to a full download whose message named only the size limit, and an mp3 fell through to the viewer whose message blamed a popup block that never happened. Both endings hid what the click actually wanted. Failures *after* the reader exists (the worker's type ack, an unrecognised session URL) are not retried — a reconnect cannot fix those — and every failure is `console.error`ed with its real error, because the fall-through messages describe the route taken, never the cause. The endings carry the failure forward: `downloadWhy` takes a `playerFailed` clause first, and the null-tab hand-off names the player failure rather than pop-ups. Pinned by `a_failed_media_open_retries_once_and_the_fallback_names_it`. The bridge's own `waitForController` (10 s, twice per click with the invalidate-retry) is what the boot handshake above keeps from ever firing: "did not take control of this page; reload once and retry" was every media click's ending while the page stayed uncontrolled, while saves merely buffered. A playing session also holds the worker's **keepalive** — `keepaliveAdd('media')` where the session is set, released in `teardownPlayer` — because Firefox's ~30 s idle kill (see the save bullet) would forget the session's taught MIME with the worker and a resume would get a 400 instead of its bytes. The worker's media route (`/__autonomi_stream/<session>/file`) is upstream's npm `dist/autonomi-stream-sw.js` **merged into ours and patched**: `nosniff` on every response and a Content-Type allowlist of `audio/*`/`video/*` only, so a same-origin route can never serve peer-supplied bytes as a document. The SDK reports `application/octet-stream` for most records — exactly what the allowlist must refuse — so the page **teaches** the worker the sniffed MIME (`av-media-type`, awaited before `video.src` is set) and a taught type that is not audio/video is ignored. Save to disk in the dialog reuses `/av-download/` with a fresh sequential reader (not the player's random-access one — the two would interleave on a reader tuned for seeking). Pinned by `the_media_route_is_the_patched_upstream_worker` and `the_inline_media_player_streams_and_saves_through_the_worker`.
- **Playback can move to a tab of its own, and that tab survives us.** The dialog's `#media-open-tab` (disabled until a session exists, like Save) runs `window.open('/media-view?…')` **synchronously in the click** (a popup after an await has no gesture), severs `tab.opener = null` by hand (`noopener` would make `window.open` return null and lose the handle), and closes the dialog only once the tab exists — a blocked popup leaves the player open with the reason on its status line. The handler touches neither `teardownPlayer` nor the keepalive: the dialog's own close path tears down as always. `GET /media-view` is a standalone player page — **the server reflects nothing** (a `const` with only the trusted `SDK_BASE` substituted, so there is no escaping question to get wrong; the page validates `address`/`type` itself and puts `name` in `document.title` only), no `app.js`, and deliberately no `connect-src 'none'` CSP like the progress page's, because its purpose *is* to make requests — what keeps it safe is that it renders no peer bytes as markup (bounded `textContent`, same 240-char clamp) and the worker's media route serves `audio/*`/`video/*` with `nosniff`. It asks `/api/blocked` **fail-closed** before any bytes (the browser-fetch egress check, restated on this new route — refusal, unreadable list and a server that is gone all end the run), imports the SDK, opens its **own** `createMediaSource` with the dialog's retry-once shape, teaches the worker the link's `type` (the SDK's own URL type is octet-stream), and pings `av-ping` itself every 10 s for the life of the page — neither page knows about the other, and neither needs to. It re-fetches the stream instead of borrowing this page's bytes, which is what makes it outlive the Anta-Vista tab entirely; the cost is a fresh connect + lookup before it plays, narrated by its own spinner and phases. One structural dependency: the document must land *controlled*, so the worker answers exactly the `/media-view` navigation with `respondWith(fetch(event.request))` (byte-identical, Host guard intact, arm *before* the `STREAM_MARKER` one) — an uncontrolled document 404s on its own media URL and the bridge's `waitForController` gives up after 10 s; a once-only sessionStorage-flagged `location.reload()` (the boot handshake's pattern) is the belt. Pinned by `the_media_dialog_can_send_playback_to_another_tab`, `the_media_player_page_reflects_nothing_and_plays_on_its_own` and `the_worker_lets_its_own_player_page_load_controlled`.
- **`is_browser_renderable` in `av-ingest` is the only copy of "can a browser display this?"** and its bias is towards no. The viewer picks `inline` versus `attachment` from it, and `/api/view/plan` reports the same verdict to the page, so the two cannot disagree. A hardcoded `inline` is what made an undisplayable type show as an empty window with no error and no download. **A hint that cannot be placed is treated as unknown, which answers "download it"** — guessing "renderable" from a generic type is how the blank window happened.
- **`detect_mime_prefix` exists because the SDK reports `raw.file.content_type || "application/octet-stream"` for most records**, so a hint-only plan downloaded every real image and PDF. It shares one private core with `detect_mime` via a `Confidence::Full | Prefix` parameter, so the two cannot drift on what a type *is*. **The rule: a prefix may confirm a specific type, never assert a generic one.** Magic bytes and the `<!doctype html` marker are positive signals that survive truncation; "this whole file is text" is inferred from the *absence* of binary structure, and a prefix cannot establish an absence — the invalid UTF-8 usually sits past the first few KB. So a prefix that decodes cleanly answers `application/octet-stream`, **not** `text/plain`, even though the same bytes as a whole file legitimately sniff as text. That is deliberate: guessing text marks the record displayable and then shows mojibake, whereas the honest answer downloads it, which always works. `a_prefix_that_decodes_cleanly_is_not_called_text` pins the contrast. Do not "fix" this by trusting the hint more, and do not add a second allowlist.
- **Progress in the opened tab is a poll, not a stream, and the reason is the library.** `tiny_http` writes a response body with `io::copy` through `chunked_transfer::Encoder`, which buffers 8 KB and never flushes between reads (`Encoder::new` sets `flush_after_write: false`, and `io::copy` does not flush). A progress log is far smaller than that, so a streamed endpoint delivers every event in one burst when the fetch ends — the blank tab again, wearing a streaming header. `web::fetchjob` (POST `/api/view/fetch` → job id, then `GET /api/view/fetch/<job>?since=N`) is the design that actually streams to the user; at 250 ms over loopback it is invisible next to a lookup that takes seconds. Do not "simplify" this back into one response.
- **The job cursor must come from the server, and the log may be trimmed underneath it.** Each event carries a sequence number and the response returns `next`; the page must send that back verbatim. A cursor counted as "events received" is only equal to the sequence while nothing has been dropped, and it stops being equal on exactly the long fetches the page exists for — either re-showing events or, if the cap outruns what was consumed, returning nothing forever while the page keeps polling a finished fetch. `a_cursor_still_works_after_the_log_has_been_trimmed` pins it.
- **An SDK `complete` is an operation boundary, not the user's download finishing.** `#openReader` reports `report(\`Opened ...\`, { phase: "complete" })` and then returns the reader — *before a single byte moves* — because the reporter's `finish()` marks the end of the `open-file` operation. Rendering it verbatim said "Fetch complete" for the entire span of a large transfer, and flashed it on small ones, which is exactly backwards for someone waiting for the resource to appear. `PHASE_LABELS` therefore has **no `complete` and no `failed` key at all**, and `reportSdkProgress` returns early on both so they cannot get through unlabelled. The transfer is announced by us instead: `fetchAutonomi` calls `onStep(PHASE_LABELS.downloading)` immediately after `openFile` resolves, and `done`/`error` remain the only terminal states the page may show.
- **The headline states what the user is waiting for; the step moves underneath it.** The h1 reads `Fetching from Autonomi…` and only `done`/`error` are allowed to rewrite it, while phases write to the detail line (`sub`). This is structural, not a wording rule: it makes it impossible for the big line to read like something already completed while the transfer is still running, which is what `Downloading done` and `Preparing the download` did. `PHASE_LABELS` values must likewise be phrased as the wait itself, never as a finished state. The old `Progress appears here as it goes.` sub-line is gone — it was true and useless, and spending the most prominent line on narrating the layout back at the reader took it away from the fetch they are waiting for.
- **Never show the SDK's own wording to a user, and let one counter own the read-out.** The SDK narrates itself in words built from what the network answered, so opening a record reports `opened public-file-3f9a2c71` — and that filename is *always* synthetic, the same one `file.name` gives and the same one we refuse to trust for a download. Beside our own counts it read as though the app had picked a file off the network. `progressLine` therefore uses `PHASE_LABELS[event.phase] || 'Fetching…'` and never `event.message`. The SDK's *byte counts* are dropped too, because we already have authoritative ones from the stream (`chunks` and `bytes` against `reader.size`); sending both to one read-out made it flicker between two formats as each fired, which reads as a broken counter. Our counts go on the `chunk` channel — the one the ant CLI diagnostics already use — so both transports render through a single element, with `expected_bytes` adding the `of 8.0 MB` that only the browser stream can know.
- **The wait needs a spinner, and it must be able to stop.** A ~6 s seed lookup with nothing moving reads as broken, which is the gap the spinner fills; it is decorative (`aria-hidden`, headline carries the meaning). `.spin` sets `display`, so `[hidden]` needs the `!important` guard — the user-agent rule lives in another origin's stylesheet and any author `display` rule silently outranks it, which would leave a spinner turning forever after a failure. Both `done` and `error` set `spin.hidden = true` as well, so the stylesheet guard is not the only thing stopping it. `prefers-reduced-motion` gets a static ring: a spinner is exactly the motion that causes trouble, and the counts beside it already report honestly.
- **Two progress channels, because the SDK mixes two kinds of event.** A *phase* is a transition and goes to the headline (`phase`); a *byte count* is continuous and replaces one `#live` line (`live`). The SDK emits `downloading` many times a second, so appending those — which is what the `status` channel does — fills the 40-line log with "1.2 MB of 8.0 MB" and pushes out the phases that tell the user the thing is still working. `#live` is `aria-live="off"` for the same reason: a count that changes faster than speech is noise. `progressLine` folds the numbers into the text, so neither side re-derives a percentage.
- **Progress updates are queued, never awaited.** `toTab` used to `await` a promise the page resolved with a `ready` message, and that failure mode is *total and silent*: a `ready` that never arrives — a dropped post, a script that threw before posting — leaves every update pending forever, with no error and no log. The tab then shows its opening sentence for the whole fetch, which is indistinguishable from a fetch that reports nothing. Updates now push onto `tab.__avQueue`, the page flushes them when it says it is listening, a `setTimeout` failsafe flushes them anyway so a dead page costs the pre-ready events rather than all of them, and the queue is bounded (`PROGRESS_QUEUE_MAX`) because the SDK reports faster than a page can be expected to load. Do not reintroduce an `await` in `toTab`.
- **A quiet progress page must say it is connected.** "Nothing to report yet" and "the opener is not talking to me" render identically, and that ambiguity is what made a broken handshake look like a progress bug. The page sets `heard` on the first message and otherwise reports that it is connected and waiting.
- **The library load is silent and it is ours to announce, not the SDK's.** The SDK's first `onProgress` fires only after `getNetworkDefaults` has compiled and instantiated 5.4 MB of WASM, and `loadSdk()`'s dynamic `import()` is silent before that — so the longest stretch of the fetch emits nothing and the tab sits on its opening sentence for most of the wait. The opener knows what it is doing at the instant it starts, so `fetchAutonomi` takes an `onStep` and says so before awaiting. **Related:** the connect is shared (next bullet), so it takes no per-operation `signal` at all — but the single-object rule still stands wherever `connect` is called: `AutonomiClient.connect(bootstrap, options)` takes its settings from a rest-spread of the *first* argument and only reads the second for the string-multiaddress form, so `connect({ onProgress }, { signal })` silently discards the abort signal. Everything goes in one object.
- **One connected client per page, never one per click.** `getSharedClient()` memoises `AutonomiClient.connect`: its promise is assigned **synchronously before the first `await`**, so racing callers share one connect instead of dialling the network twice, and a failed connect clears the slot (`sharedClientPromise = null` in the catch) rather than condemning the browser route until reload. It replaced a fresh client per open/index/save that was **never closed** — a leaked WebRTC association per click — and made every one of them re-pay the WASM compile and the seed dial. A shared client can outlive the connection under it, so `openAutonomi` wraps `openFile` with **invalidate-and-retry-once**: a non-abort failure drops the shared client (`invalidateSharedClient()`), reconnects and tries once more, and the repeat failure — the file's fault, not the connection's — reaches the caller and from there the daemon route. Stop is excluded from the retry by **ordering**: the abort checks (`signal.aborted`, `DownloadCancelled`) throw before the invalidate can run, so stopping can never spend a reconnect. The player, the save and indexing all ride the same client. Pinned by `the_client_is_connected_once_and_the_abort_stays_with_the_reader`.
- **Progress counts describe the transport that actually ran, and the two cannot be reconciled.** WebRTC reports phases and `completed`/`total` bytes; the ant CLI reports *distinct successful chunks* and *diagnostics bytes read*, deduplicated by `chunk_index`, because self-encryption padding means they are never a fraction of the file — a bar that stalls at 99% is a lie, so there is no bar. antd is indeterminate. `Open` names the transport that ran it ("via your browser" / "via the local daemon") rather than a single "indexed".
- **A failed fetch explains itself in the tab it opened.** `GET /view/error?code=<enum>` is a standalone page: no app.js, no stylesheet, no API access, and a fixed code-to-message table. The tab is no longer closed on error — a tab that vanishes leaves the explanation behind it, in a row on a page the user must go back to. **The only input is that enum**, so an SDK error string can never be reflected; it is written into the row's status line with `textContent` instead.
- **Opening a tab severs `window.opener` by hand: `tab.opener = null`.** `window.open`'s `noopener` feature cannot be used here because it makes the call return `null`, and the handle is what the finished file is loaded into. Cross-origin stops a fetched document *reading* the app, but nothing stopped it *navigating* the app, and peer-supplied HTML is exactly the untrusted input. `js_code` in `web_tests.rs` strips comments before asserting this, for the same reason `css_rule` does.

- **`window.open` must happen synchronously, before the first `await`, from whatever starts the open.** A click on the location calls `openView`, whose `runOpen` opens the progress tab before anything awaits — a popup opened after an await has no user gesture and browsers block it. The one deliberate exception: a row whose stored `result.mime_type` is audio or video (`likelyMedia`, decided **before any await** — the player in this page is the display, and a tab that appeared only to close again was the choreography users reported) opens **no tab at all**, with the phases landing on the row's own status line instead. `trustStoredMime` is dropped at the null-tab hand-off if such a row turns out to need a display after all, so the "Allow pop-ups … try Open again" message can never deadlock — the next click opens the tab normally; a popup the browser blocked teaches the row nothing and does not flip. Pinned by `an_autonomi_location_looks_clickable_because_it_is` and `a_media_row_opens_no_progress_tab_and_reports_on_its_own_line`.
- **`app.js` is a classic script, so the SDK must be `import()`ed dynamically**, lazily, from `window.__AV_SDK_BASE__`. Loading it eagerly would make page load wait on 5.4 MB of WASM. `loadSdk()` caches the promise *including its failure*: a browser that cannot run it should say so once, not on every click. `autonomiCapability()` asks the SDK's own `getBrowserCapabilities()` once and states the reason on the location's title rather than offering a control that fails.
- **The SDK wants a bare 64-hex address.** `autonomiAddress()` strips `autonomi://` and any `/name` or `?name=` segment; a scheme-prefixed value is rejected with a misleading "expected 32 hexadecimal bytes". `autonomiAddress()` returning `null` means "not an Autonomi link" and the row is left as plain text — **never an `autonomi://` href**, since nothing handles that scheme.
- **Never trust the SDK's filename.** `file.name` is always a synthetic `public-file-<8hex>.bin`, so every saved file would land under the same meaningless name. The server supplies the name instead, from `av_ingest::filename::suggest_filename`, sanitized to one path segment because it is attacker-influenced and ends up in a download directory.
- **An Autonomi record's name lives in `resources.filename`, and reaching it is the awkward part.** `analyze_location` splits a location into `canonical` (the bare address — the record's *identity*, load-bearing for dedup, for the block bridge and for `autonomiAddress()`) and `inferred_filename` (the author's `/welcome.md`). `ingest_bytes` stores both, but `cmd/search.rs` projects `location_canonical` as the result's `location` and so **cannot show the name**, and the page echoes that bare address back in `X-Anta-Uri`. Anything that derived a name from the request URI therefore saw no name at all: a record published as `autonomi://<hex>/welcome.md` downloaded as `52af8a181c6171f8.md`. `resources::find_filename` closes that gap by matching `location = ?1 OR location_canonical = ?1`, and `suggest_filename_with` takes the result as a `known_name`. **Precedence is URI segment/`?name=` → stored `filename` → address + sniffed extension**: the link in front of the user is live intent and a stored name must not mask it. Do not widen `get_by_location` instead — it feeds `av_index::naming::resolve_target_resource`, the name→resource blocking bridge. `location_canonical` is **not unique** (one record indexed under two paths is two rows), so the lookup is `ORDER BY created_at DESC` for a deterministic pick.
- **The stored name reaches all three file-naming routes, and they must agree**: `/api/view/plan` (naming a download), `/api/view/blob` (opening in the viewer) and `resources.filename` in the search row. `stored_filename` in `web/handlers.rs` is the one lookup, and a read failure there is deliberately **not** fatal — it is a best-effort improvement to a label with a safe fallback, not a policy decision, so it must not be confused with the block readers that must fail closed.
- **The viewer's token is the entire authorization; the filename is decoration appended to it.** `/v/<uuid>/welcome.md` titles the tab, because an inline `Content-Disposition` cannot: it sets no tab title and no download default. `respond`'s match therefore accepts the bare token **or** the token plus exactly one segment, and the token alone still works so a viewer that never learned a name can be opened. The segment is validated, not trusted — the request line is attacker-controlled — and `path_is_ours` accepts URL-unreserved characters *and well-formed percent triplets* because `path_segment` emits `%20` for a space, which `suggest_filename` permits. A charset check that stopped at the unreserved set made every space-named file 404. `%2e%2e` and `%2f` are refused even though the segment never locates bytes, so traversal is not one refactor away.
- **`filename=` belongs on *both* dispositions.** A bare `inline` (the old behaviour) makes the browser answer its own "Save image as…" with the last path segment — the uuid, untyped — so right-clicking a picture the user had just opened produced a file the OS could not open. Note `disposition_of` must add **one** pair of quotes: `quoted_body` supplies them, and a second pair is how this briefly emitted `filename=""x""`.
- **A download is named from the location, and an extension is added only when the author left one off.** The author's own name wins: a trailing path segment, else `?name=` (which used to be ignored entirely — a path-less `autonomi://<hex>?name=report` fell back to an address-derived name, even though the location layer had parsed it all along). The name comes from `location::last_url_segment`/`analyze_location` rather than a second hand-rolled split, so percent-decoding cannot drift. **An extension that is already there is never replaced** — an unrecognised one is still the author's, and overriding it would let the content rename the file they published. When there is none, the sniffed type supplies one (`photo` + JPEG → `photo.jpg`), because a file saved as `photo` is one the OS cannot open. `trusted_extension` in `av-ingest` is the single definition of "has an extension" for both this and the type-tie-breaking in `detect_mime_with_hint`: a name we would not break a MIME tie on is also a name we will not append to.
- **`extension_for_mime` is the exact inverse of `HINTED_TYPES`, and the pairing is pinned.** A type we are willing to *resolve* on a name must also be a type we can *name* — they answer the same question from opposite directions ("what does `.csv` mean?" and "what do we call a `text/csv`?"). They disagreed for ten types (`image/avif`, `text/csv`, `audio/flac` and others could be resolved but never named, so a file the user's own URL identified was downloaded as an untyped blob), and nothing but `every_type_we_would_resolve_can_also_be_named` would have caught it, because adding to either list alone looks correct.
- **`text/markdown` is recognised by convention, not signature, and is deliberately *not* renderable.** `infer` has no magic number for markdown, so `looks_like_markdown` looks for a convention instead: front matter, or an ATX heading opening the file. This is acceptable where the HTML marker is not, because both candidates are *text* — a false positive is `text/markdown` for a really-plain file, whose only consequence is whether the saved file is called `.md` or `.txt`. It is not renderable because a browser handed `text/markdown` treats it as an unknown type and downloads it, so claiming otherwise is exactly the blank-window case `is_browser_renderable` exists to prevent. Recall is partial and that is fine: a markdown file opening with a paragraph has no marker and keeps the `text/plain` answer rather than being guessed at. The marker only runs after the bytes decode as UTF-8, so it cannot talk a binary into being text.
- **Stream the record; do not call `download()`.** `download()` waits for the whole file and reports **once, at the end** (`phase: "complete"` plus the final byte total), so it says nothing for the entire duration of the transfer — the one thing a progress display exists to cover. `openFile()` + `reader.stream()` is what makes a live count possible, and it gives two things `download()` never exposes: `reader.size`, known from the DataMap *before* any chunk moves, and plaintext a chunk at a time. try.autonomi.com shows per-chunk progress for exactly this reason. Accumulate the parts into a Blob at the end — the caller still needs the whole file, so peak memory is unchanged and the gain is observability, not footprint. Check `received === reader.size` before returning, or a short stream passes for a complete file.
- **Recognise a byte event by its counts, never by its phase.** The SDK's `progressReporter` holds a single `current` object and does `current = details` on every report carrying details — so a byte update that passes `{ completed, total }` without repeating `phase` **erases** the phase. `progressLine` and `reportSdkProgress` therefore test for the counts themselves; gating on `phase === 'downloading'` drops the numbers from exactly the events that carry them, which presents as "the download shows nothing until it finishes".
- **Subscribe to progress on `connect()` *and* the open/stream.** The phases a user watches — connecting, looking up which nodes hold the file — are emitted during `connect()`, while the byte and chunk counts come from the stream consumed afterwards. Either alone leaves a gap: the reader is silent for the ~6 s a lookup takes, which is exactly when a user concludes it is broken. Key failures on `err.code` (`DOWNLOAD_FAILED`), never on message text; a nonfatal `WebRTC: ICE failed` is seed failover, so only a settled failure is reported.
- **`window.open` must happen synchronously, before the first `await`.** A popup opened after an await has no user gesture behind it and browsers block it, so the tab is opened on click and `location.replace`d once the URL arrives. If the tab was blocked, say so and keep the bytes — do not silently drop them. The `likelyMedia` no-tab exception in `runOpen` (above) does not weaken this: it applies to known-media rows only, where there is no tab to block and no URL to arrive — every other open still hands its tab over before its first await.
- **Browser-first indexing falls back to the daemon *explicitly*.** `indexAutonomiInBrowser()` returns `null` for a non-Autonomi location (a decline, not a failure) and throws `DaemonFallback` when the browser cannot or should not fetch — no capability, a failed WebRTC transfer, or a file over `MAX_UPLOAD`. `DaemonFallback` is a *routing decision*, never shown to the user as an error, and the success message names the transport that ran ("via your browser" / "via the local daemon"), because "indexed" otherwise means two different things. The size check is **before** the upload: the bytes are already in hand, so sending them to be rejected wastes the transfer.
- **`MAX_BODY` is refused, never clamped.** `read_body_bytes` reads one byte past the cap and answers `400 body_too_large`; the old JSON `read` truncated via `Read::take`, which for these endpoints would have indexed a *corrupt prefix* of a large file under the resource id of those partial bytes and reported success. The refusal carries `RouteError::Ready`, not `Internal` — collapsing it would report a client-side limit as a 500.
- **`/api/index/bytes` spools to a temp file and refuses over 512 MiB, never clamped.** The body is first streamed to a fresh `create_new` temp file (`av-index-<pid>-<nanos>`) via `read_body_to_temp`/`copy_capped_to_path` at `INDEX_BODY` (512 MiB), then `fs::read` into the unchanged `index_resource_from_bytes`; the temp file is removed on every path (over-cap refusal, read error, success). Over-cap answers `400 body_too_large` with the file already deleted. The client mirrors the constant as `MAX_INDEX_UPLOAD` (`indexAutonomiInBrowser`'s pre-upload check); `MAX_BODY` (32 MiB) is unchanged for `/api/view/blob` and remains the viewer cap. `index_body_cap()` reads the `ANTA_VISTA_INDEX_BODY_CAP` env seam (parse > 0, else the default) so the refusal test can post cap+1 against a lowered cap without allocating 512 MiB. Pinned by `an_oversized_upload_is_refused_rather_than_truncated` and the `#[cfg(test)] mod tests` suite in `server.rs` (at-cap kept, over-cap refused + file removed, empty allowed, cap default > `MAX_BODY`).
- **The viewer's separate port is a security boundary, not a convenience.** Fetched bytes are served by a throwaway `127.0.0.1:0` listener at `/v/<uuid-v4>`, inline, `nosniff`, `no-store`, `no-referrer`, GET/HEAD only, loopback `Host` only, expiring in 120 s. A second port is a second origin, so a hostile document cannot reach `/api/*` — and the `Sec-Fetch-Site: cross-site` guard on POST is the second half of that same protection, because a different port *is* a different site. **Relaxing either half makes serving `text/html` and `image/svg+xml` unsafe**, so those two MIME hints are licensed by this pair, not by the sniff policy alone. There is no cookie and no shared secret: the unguessable token path is the *entire* authorization, and `the_viewer_only_serves_its_own_token` pins that a neighbouring path is a 404.
- **The MIME policy is shared, and it is extension-over-generic only.** `detect_mime_with_hint` lets a short, alphanumeric extension break ties *only* where sniffing is weak (`text/plain` / `application/octet-stream`); content always wins when it is specific, so a `.html` name cannot turn a real PNG into markup. This lives in `av-ingest` rather than the web layer so a stored `mime_type` and the type a download is served as cannot disagree. `detect_mime_with_hint` is also what a `.html`/`.svg` record needs to have any extractable text to embed at all.
- **A `.ant` manifest is summarised, never expanded.** Bytes starting `C1 41 4E 54 01` sniff as `application/vnd.autonomi.manifest` (`ANT_MANIFEST_MIME`) by magic alone — the type is deliberately **not** in `HINTED_TYPES`, so a text file merely named `.ant` keeps its real sniff and only content ever asserts this type, while `extension_for_mime` still maps it back for naming (the pairing tests iterate `HINTED_TYPES`, so this asymmetry is free). `av_ingest::ant_manifest::summarize` is a display-only bounded walk of the ADR-0006 msgpack body at strictness parity with upstream's decoder (64 MiB input cap, depth 16, unknown ContentRef variant = hard error, trailing bytes = error, non-str keys skipped as unknown, duplicate known fields = error, path rules ported from upstream `path.rs`, the upstream `GOLDEN_V1_HEX` fixture pinned as a test) with one documented carve-out: no effective-name collision check, because extraction is the only consumer and acting on it would need address derivation. It feeds `extract_ant_manifest` — title from the manifest's `name`, first 500 entries plus the true `entry_count` in `metadata_json` — and the `synthesize` description (`an autonomi file manifest titled "…"` listing the paths; when only the first 500 were stored, the base carries `with N entries` and the list is **empty**, because a partial list's fill tail would claim the prefix is the whole). `ResourceKind::Manifest` rides through the store kinds and `--kind manifest`.
- **A manifest link is refused precisely, and expansion waits for upstream.** `autonomi://manifest/<unpadded base64url of the complete .ant bytes>` — authority literal, payload verbatim, because base64url is case-sensitive; `?`/`#`/a further path/padding all fall through to the ordinary address parse — is recognised by `parse_manifest_location`/`is_manifest_link` in `av-ingest::location`. Its bytes travel in the link, so there is nothing on the network to fetch: one shared message (`manifest_link_error`) refuses it from `av index` **before** the antd gate could offer to install a daemon for it, from `index_resource` (covers the web), from `verify_uri_exists` (so `av name` does not go hunting for a backend) and from `download_content` as a backstop (covers both web fetch routes). `is_manifest_link` runs the parser rather than testing the canonical for the prefix, because a *failed* manifest parse falls through with its raw text as the canonical and that text starts with the prefix too. **Child-row expansion — indexing a link as its children, browser-side link decoding — is deferred until upstream PR #6 (`feat/manifests`) ships and ADR-0006 leaves "Proposed";** the vendored SDK is 0.1.2 and has no manifest API, so do not half-build it in the meantime.
- **Known gaps — do not paper over these in the UI.** `Open` fetches **one record**: a single-file viewer, so *absolute* `http(s)` subresources load but *relative* ones fail, and `autonomi://` subresources are unreachable without a browser-side crawl that does not exist yet. `try.autonomi.com` itself is a multi-file site behind a strict CSP and will *not* work as one blob. Multi-file expansion is expected upstream rather than reimplemented here; anta-vista now *summarises* a `.ant` manifest at ingest but never expands one into the files it names. Downloads are also bounded by the DataMap's reachable seed set, which is small; a very large file can time out even though a small one succeeds.

## Local blocking
`blocks` table, migration `005_blocks`, repo at `crates/av-store/src/repo/blocks.rs`. Three **independent** kinds: `resource` (`resources.id`), `name` (`name_records.record_id`), `agent` (64-hex x0x id). CLI in `crates/av-cli/src/cmd/block.rs`; web at `/api/block`, `/api/unblock`, `/api/blocks`.

- **The invariant: a blocked resource is never served, and a blocked agent is never consulted.** Any new egress path must re-check. Current guard points: `av_index::search::search_top_k` and `av_index::naming::lookup_name` (primary — also what the responder reads from), `to_publishable_resources`/`to_publishable_names` in `cmd/listen.rs` (pre-send, catches `--keep-local` resources that still have embeddings), the `--x0x` agent filter in `network.rs` (both candidate lists and response drops), `propagate_resource` (shared by `av propagate`, the search prompt and the web rating handler), an early refusal in `cmd::index::index_resource` before any store write, and `refuse_if_blocked` on every web route that fetches or writes on the user's behalf — `GET /api/download`, `POST /api/view/fetch`, `POST /api/view/plan`, `POST /api/index`, `POST /api/index/bytes` (the content-hash check inside `index_resource_from_bytes` cannot stand in for the location check: a deleted block leaves no row for new bytes to collide with) and `GET /api/blocked`, which answers the page's **pre-fetch** `checkBlocked` question with the *same* 403 `blocked` shape every fetch route gives — one refusal shape, so the page and the server cannot disagree about what is blocked. Fails closed: a `blocks` read error is `503 block_check_failed`, never a go-ahead. The fetch routes are the ones that need a table of their own; see below.
- **A fetch is handed a location, and a resource block is keyed by content hash — so the location has to be recorded before the block deletes the row.** `is_location_blocked` cannot be a join on `resources`: `av block` deletes the local copy by default, so the row a fetch guard would need is the row the block just removed, and the guard answers "not blocked" for exactly the resources a user blocked. That failure reads as the block being ignored rather than as the guard being unable to find it. `blocked_locations` (migration `007_blocked_locations`) is the fix: `record_blocked_locations` writes **both** spellings — `location` *and* `location_canonical` — before the delete, and `is_location_blocked` reads it first, keeping the join only as a fallback for pre-007 blocks and `--keep-local` resources that still exist. `a_location_stays_blocked_after_the_blocked_resource_is_deleted` is the test that pins the ordering; a version of this guard that only joined would pass every other test here.
- **`blocked_locations` is keyed by `(resource_id, location)`, and both halves are load-bearing.** The `location` is what a fetch matches; the `resource_id` is what lets `av unblock` clear it — re-reading `resources` to find the spelling would find nothing, because the block deleted the row, leaving a refusal the user cannot lift through the API. `forget_blocked_locations` deletes by id; a `--kind resource` clear enumerates ids via `resource_ids_with_blocked_locations`; `unblock --all` calls `forget_all_blocked_locations`. The table has no `subject_kind` because every row in it is a resource block by construction. Recording is idempotent and unconditional — including under `--keep-local`, since that resource can be purged later and a block that lapses when the file is cleaned up is not a block. It is a **fetch-level** deny list: a location stays refused until explicitly unblocked even if different content later appears at that address, because a fetch by address has no content to compare and refusing is the safe direction to be wrong in.
- **A name block is not a resource block.** `NameRecord` stores a URI, not a `resources` id, so a resource block has to be bridged by resolving the target through `resources::get_by_location`. `av_index::naming::retain_unblocked_targets` is that bridge, and both name-serving paths call it: `lookup_name` (which the responder reads directly) and `to_publishable_names` in `cmd/listen.rs`. `cmd/name.rs` and `cmd/index.rs` both normalise with `av_ingest::location::normalize_uri`, so `target` and `resources.location` share a form; `target_canonical` is the fallback for records that arrived from a peer carrying the legacy `ant://` scheme. The bridge only recognises targets this machine still holds, so after a *delete* there is nothing left to resolve against and a re-supplied claim can be served — see `docs/known-limitations.md`. Do not treat "unresolvable" as "blocked": dropping every name whose target is not held locally would let one block censor the whole local namespace. Do distinguish *not held* from *lookup failed*: `resolve_target_resource` returns `Ok(None)` for the first and `Err` for the second, and the `Err` must propagate. Collapsing them with `if let Ok(Some(..))` turns a broken `resources` table into "we hold nothing", which is the fail-open bug this file already warns about elsewhere.

  All three block kinds that can affect a name now load through one place, `av_index::naming::NameBlockPolicy::load`, and are applied by `retain_unblocked`. `lookup_name` and `to_publishable_names` both call it, which is the point: they used to open the block table separately and could drift. Add a block kind by extending the policy, never by reading `blocks` in a caller.
- **Do not add a provenance column to `resources` to enable resource→agent blocking.** The kinds are independent by design: anta-vista does not know who sent a resource, and inferring it would let one bad result condemn a useful peer. `ClusteredResult.agent_ids` preserves transport origin for *display* so a human can block a peer deliberately.
- **`name_records.origin_agent_id` is the one provenance column, and it is local-only.** Migration `006_name_origin`; the field is `#[serde(skip)]` on `NameRecord`, and `types.rs` tests pin that a peer cannot set or see it. A name block by resource id is bridged through the target, but an *agent* block has nothing to match without it, because `NameRecord.by_agent_id` is self-reported. `retain_unblocked_agents` therefore matches on `origin_agent_id` only. Populate it in the one place that holds the authenticated sender, `cmd::resolve::run`'s cache loop, via `names::insert_with_origin`; plain `names::insert` leaves it NULL and is for locally authored records. NULL is also what pre-006 rows look like, and they are deliberately left unfiltered — a blocked peer cannot be attributed retroactively. Do not start filtering on `by_agent_id`; `a_peer_cannot_hide_behind_an_id_it_wrote_itself` exists to stop exactly that.
- **Never gossip blocks.** They are local policy; a peer learning about them is a privacy leak.
- **Identity comes from the transport, not the envelope.** Blocked-agent matching uses `DirectMessage::sender` / `IncomingEvent::origin`, not the self-reported `from_agent_id` — otherwise blocking is trivially bypassed by editing the envelope.
- **Unblock is not undo.** `block --resource` deletes the local copy by default; `--keep-local` is the escape hatch. Unblocking lifts the row and cannot restore deleted data. Never word a response as though it restored anything.
- **Partial x0x success is reported, not hidden.** `BlockOutcome::x0x_applied` is `None` (not requested), `Some(Ok)` or `Some(Err)`; the local block lands regardless. `av unblock --all` deliberately does **not** lift transport blocks, because it cannot enumerate x0x contacts.
- Agent ids are validated as 64 hex. A mistyped id stored as a block silently never matches anything, which reads as "the block is working".
- **Block policy reads must fail closed.** A `blocks` read that errors is not evidence that nothing is blocked, so `blocks::blocked_ids` propagates instead of returning an empty set, and every caller on a serving path (`search_top_k`, `lookup_name`, both `to_publishable_*` in `cmd/listen.rs`, `cmd/index.rs`, `propagate_resource`) propagates too. `unwrap_or_default()`/`unwrap_or(false)` in any of those is a latent "serve everything the user suppressed" bug — there is a test that drops the `blocks` table to pin this.
- **One block report, read once.** `cmd::block::block_report(conn)` returns the list *and* the per-kind breakdown from a single `list_all`, and both `av block --list` and the web `/api/blocks` call it. They used to each issue their own two queries and build the same JSON by hand — byte-identical, and therefore free to drift — so a block landing between a `COUNT(*)` and a `SELECT` produced a summary whose parts did not add up to its total. Replaying that shape against a concurrent writer disagreed 106/2000 times (~5%), which is why it passed every ordinary run; `the_breakdown_holds_while_another_thread_is_blocking` now asserts the invariant in a loop, and the invariant holds by construction rather than by luck. `blocks::counts_by_kind` is deleted, so there is exactly one way blocks are counted.
- **`blocks.subject_kind` has no CHECK constraint, so it can hold a value `BlockKind` cannot represent.** `BlockEntry` therefore carries `subject_kind_raw` alongside the parsed `subject_kind`, and the report groups and labels on the raw string. Parsing first would file an unrecognised kind under `resource`, and a UI looking up `resource` would find a number that does not include it. Use `subject_kind_raw` to *display* a subject and `subject_kind` to *match* one.
- **Never print an abbreviated id where a block argument is expected.** A block is keyed by *exact* match, so `av search`/`av resolve`/`av block --list` print full ids. Re-introducing `abbrev(&id, 16)` there silently makes the feature unusable. These lines deliberately do **not** print a ready-made `to block: av block --…` command — it was tried and removed as noise; the id plus `av block --help` is the intended path. Peer ids are hidden behind `av search --show-peers` (and always present in `--non-interactive` JSON) because the count is already in the result header and printing every id is unusable at real cluster sizes. `expand_known_prefix` in `cmd/block.rs` additionally refuses a short id that is a strict prefix of a locally-held subject and prints the full id; the `LIKE` there must use two placeholders (`?1` pattern, `?2` exact id) or a full id matches itself and nothing can be blocked at all. An id we do *not* hold is a normal network result, so that case is allowed and only warns. `unblock` checks for an existing exact row *before* the prefix check, or a dead short block left by an earlier build could never be removed except with `--all`.

## Config
- TOML via `AvConfig::from_file(path)`; all fields optional; `validate()` checks ranking weights sum to 1.0 (tolerance 0.01).
- **Two independent weight schemes — don't confuse them.** `AvConfig` defaults (`av-core/src/config.rs`): semantic=0.65, agreement=0.15, feedback=0.10, trust=0.10 (validated). But `av-core/src/constants.rs` has a *different* 5-weight set (semantic=0.55, relevance=0.10, agreement=0.15, feedback=0.10, trust=0.10) used by `av-trust::ranking`. Also name-ranking constants (`NAME_WEIGHT_*`). The constants set is not validated against config.

## Key dependencies & quirks
- `fastembed` v4 with features `["ort-download-binaries", "hf-hub-rustls-tls"]` — declared inline in `av-embed`, not a workspace dep.
- `rusqlite` with `bundled` feature everywhere — every `av-store` connection enables WAL mode, `PRAGMA foreign_keys` **and `PRAGMA busy_timeout=5000`** (see `crates/av-store/src/db.rs`). Declared inline in `av-trust`/`av-query` despite being a workspace dep; depends on same spec. The busy timeout is load-bearing: the web server opens a connection per request and the responder opens its own, so writes overlap, and SQLite's default of 0 turns a momentary overlap into an immediate `SQLITE_BUSY`. For the same reason, anything that reads-then-writes must use `BEGIN IMMEDIATE` (`blocks::delete_resource_cascade_with_names` does it by hand, because rusqlite's `transaction*` methods need `&mut Connection` and these callers hold `&Connection`) — a deferred transaction that upgrades from read to write fails with `SQLITE_BUSY_SNAPSHOT` if anything else committed in between.
- **Two SQLite races that `busy_timeout` does *not* save you from, both fixed in `db.rs` and worth knowing before touching it.** (1) `ALTER TABLE ADD COLUMN` is not idempotent, and `migrate` is reached concurrently by several threads opening a fresh database, so they all see a migration as pending and all run its DDL — the loser died on "duplicate column name". `migrate` now takes `BEGIN IMMEDIATE` and re-checks `applied_migrations` *inside* the write lock, so the loser waits and then sees it recorded; `INSERT OR IGNORE` alone was not enough, and neither was assuming the DDL is idempotent (`CREATE TABLE IF NOT EXISTS` is, `ALTER TABLE` is not). (2) `PRAGMA journal_mode=WAL` needs a lock no other connection will grant and SQLite answers `SQLITE_BUSY` there **without consulting `busy_timeout`**, so a burst of opens made `open` fail intermittently and took the web server down. `ensure_wal` re-reads the mode and accepts the winner's WAL instead, since WAL is a property of the file, not the connection. Note also that `busy_timeout` is per-connection, so it must be the *first* statement in `configure` — anything ordered before it runs with the default of 0.
- `ureq` (sync HTTP) — no tokio or async runtime in the project. The web server is `tiny_http` on plain threads, not an async runtime either.
- `tiny_http` 0.12 — its `unblock()` releases only one waiting thread, so shutdown is polled instead (see Web interface).
- `infer` for MIME detection — `kamadak-exif` for image metadata, `id3` for audio (`av-ingest`).
- `directories` for platform data paths — defined in `av_core::paths`.
